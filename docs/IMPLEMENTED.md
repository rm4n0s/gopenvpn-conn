- **Learned:**
  - The plan's Facts for `tls-crypt` were exactly right (SPEC §21 O9). Note the HMAC input is in wire order, the opposite of `tls-auth`: a place where copying one wrapper to make the other would have been wrong.

## Step 1.8: the reliability layer (2026-11-21, tag `step-1.8`)

- **Built:** `internal/reliable`, with no I/O, no goroutine and no clock:
  - `Sender` (`NewSender(initialTimeout)`, `CanSend`, `Len`, `Queue`, `Due`, `NextDeadline`, `Ack`) and `Outgoing`: ids from 0, a window of 6, the wait of 2 s that doubles up to 128 s, the fast retransmission after three later packets are acknowledged, the opcode kept for each packet (a reset or a `CONTROL_WKC_V1` stays what it was when it is sent again).
  - `Receiver` (zero value ready; `Receive`, `HasPendingAcks`, `Acks`): in-order delivery with a window of 12, acknowledgement of copies, a list of at most 8 acknowledgements to send, and the repetition of recent ones in later packets.
  - The constants `SendWindow`, `ReceiveWindow`, `MaxAcks`. Ids are compared as serial numbers, so wrapping works (tested).
- **OpenVPN files used as reference:** `reliable.c` (`reliable_send`, `reliable_send_purge`, `reliable_send_timeout`, `reliable_mark_active_outgoing`, `reliable_wont_break_sequentiality`, `reliable_not_replay`, `reliable_ack_write`, `copy_acks_to_mru`), `reliable.h` (the constants), `ssl.c` (`tls_pre_decrypt`, the receive side). The structure is not theirs: a slice of entries in id order for the sender, a map of early packets for the receiver, and "due" lists instead of one buffer at a time.
- **Checks that ran:** `scripts/check.sh`, all thirteen OK. There is no parser in this step, so no fuzz target; the property test takes its place.
- **Tests:** the retransmission times (sent at 0, 2, 6, 14, 30, 62, 126, 254, 382 s), the window of 6 (and its error route), the fast retransmission, repeated acknowledgements counting once, wrapping ids, the opcodes kept, receive windows (the last id kept, the next dropped), copies acknowledged, the list of 8 acknowledgements, the repetition of recent ones (newest first, 8 at most), the room of a packet. The property test runs a `Sender` and a `Receiver` over a simulated link in virtual time (no real sleep): 6 kinds of link (clean, reordering, duplicates, 10%, 30% and 60% loss) times 12 fixed seeds; each time all 150 payloads arrive once, in order.
- **Learned:**
  - The plan's Facts are right. One thing they leave open: OpenVPN acknowledges a copy of any older packet, and keeps a packet that is up to 11 ahead; both are as the Facts say, and are in SPEC §7.2 now.
  - **A deviation (SPEC §20 V6):** OpenVPN's fast retransmission counts every acknowledgement of a later id, and the peer repeats ids in each packet, so one lost packet followed by one acknowledged packet whose ack is repeated three times is sent again at once. The code counts each later packet once. The wire is unchanged.
  - A receiver that kept every early packet and acknowledged all of them would let a peer grow the list of acknowledgements without bound; the list is capped at 8 as the packet format requires, and a packet that finds it full is dropped to be sent again.

## Step 1.9: `Conn`, the in-process peer, and the three-way handshake (2026-11-21, tag `step-1.9`)

- **Built:**
  - `internal/session`: `Session` (`New`, `Handshake`, `Close`, `Link`, `Dropped`), `Options`. Two goroutines: a reader of the link (datagram, or stream with the 16-bit frame) and a loop that owns every piece of state, writes the link, and runs the two timers (the retransmissions of `internal/reliable`, and the handshake timeout). The loop closes the link when it ends, so a failed session leaves no goroutine; `Close` waits for both. The error that ends a session is stored once (`fail`) and every later `Handshake` returns that value. A packet is checked in the order of SPEC §15: its protection, its parse, its session id, and only then is anything in it used.
  - `internal/vpntest`: `NewDatagramPair` (a link in memory with loss, duplicates and delays from a seed, with deadlines), `NewStreamPair` (`net.Pipe`), `NewServer` (written apart from `session`: it answers the reset, acknowledges, sends again with `internal/reliable`, strips the wrapped key of `tls-crypt-v2`, and can be silent, acknowledge a wrong session, or `Inject` a packet of its own making).
  - Package `openvpn`: `Config` (`ControlWrap`, `HandshakeTimeout`, `Logger`), `ControlWrap` with `NewTLSAuth`, `NewTLSCrypt`, `NewTLSCryptV2` and `KeyDirection`, `Client`, `PacketClient`, `Conn` (`HandshakeContext`, `Close`, `LocalAddr`, `RemoteAddr`, `NetConn`), the exported tags `TagHandshakeTimeout` and `TagLinkFailed`. A `Config` that cannot be used makes the `Conn` fail at birth (`Options.Err`) because `Client` cannot return an error.
  - `internal/ctrlwrap`: `HashFor` (the digests of `tls-auth`; it keeps the SHA-1 import in the one package that has the lint exclusion).
- **OpenVPN files used as reference:** `ssl.c` and `ssl_pkt.c` (the order of the checks of an incoming control packet, the third packet, `tls_pre_decrypt`), `reliable.c` through step 1.8. The structure is not theirs: no state per key slot yet, a loop that owns the state instead of a function that is called by a big event loop.
- **Checks that ran:** `scripts/check.sh`, all thirteen OK. No parser in this step, so no fuzz target.
- **Tests:** `TestHandshake` for datagrams and a stream, each with the four protections (and the server asking for the wrapped key, or not): the server sees a reset with id 0, no acks and no payload, then an `ACK_V1` (or a `CONTROL_WKC_V1` with id 1) that acks it; 30% loss, duplicates and delays, and all of it together, 8 seeds each, over every protection; the reset is sent again at 0, 2, 6, 14 and 30 seconds (virtual time); a silent server gives `TagHandshakeTimeout` after exactly `HandshakeTimeout`, and the same error comes back at the next call; a cancelled context and an expired deadline; a server that acks another session, and one with another key, give a timeout and count the drops; strangers' packets with the right protection but another session id change nothing (3 dropped, nothing sent); garbage of every shape is dropped and counted; after `Close` no goroutine is left, the link is closed, and the next call gives `net.ErrClosed`; a failed write, a stream that ends, a frame that is cut, a link whose `Close` fails (both before and after the start) each have their route. The tests of the public package do the same through `Client` and `PacketClient`, and check that a `Config` is shared by connections and not changed. `internal/vpntest` has tests of its own for the link: boundaries and order, a buffer that is too small, loss, duplicates, reordering by delay, the same faults for the same seed, deadlines (also one that is set while a `Read` waits), and `Close`.
- **Learned:**
  - `net.Pipe` has no buffer: if the client and the server both write while each one's reader waits for its own loop, they wait for each other. Both ends have a queue of 128 packets between the reader and the loop, and the tests that have no server read what the session writes.
  - The real server starts no session from an `ACK_V1` alone (SPEC §21 O7, O11); in the finished client the third packet is the ClientHello. Until step 1.11 the handshake therefore ends with the acknowledgement being sent, and this is written in SPEC §7.3.
  - A write to the link that blocks (a full TCP buffer) stops the loop, and so the handling of what arrives. It ends when the link is closed, so `Close` always works. A separate writer goroutine is for a later step if a test needs it.

- **Proof (the real server 2.7.9, `--disable-dco`):** `TestEchoWithRealServer`: UDP and TCP × four ciphers × the epoch format and the 32-bit one (bit 10 left out): 100 echo requests in a row each, 16 rows. Server log: `Outgoing Epoch Data key 1: Cipher 'AES-256-GCM' initialized with 256 bit key`, `Incoming Epoch Data key 1: ...`. `TestEpochsAdvanceWithRealServer`: a client limit of 60, 600 echo requests, UDP and TCP × AES-256-GCM and CHACHA20-POLY1305: the server logs `Received data packet with new epoch 67. Updating receive key` and every request is answered (SPEC §21 O21).
- **Learned:**
  - A race in step 2.3, found by a flaky test during this step: `extendHandshake` handed the new end to the loop through a channel of one place and dropped the old value, so two `AUTH_PENDING` messages in a row could leave the shorter. The latest end is kept under the session's mutex now, and the channel only wakes the loop; `TestExtendHandshakeKeepsTheLatestEnd` tests it without timing.
  - With the epoch bit announced the real server uses epochs for every test, so the 32-bit format would no longer be exercised by the real-server tests: the `noEpoch` knob keeps it.
  - Epochs are as strict as the receive window says: a sender that moves ahead faster than the peer's receiver can follow (a one-way flow with a tiny limit) is not opened. The real limit, 2^36, makes this unreachable in practice.

## Step 2.7: keepalive (2026-11-22, tag `step-2.7`)

- **Built:**

  - Package `openvpn`: `Config.PingInterval`, `Config.PingTimeout` (negative is an invalid config), `TagPingTimeout`.
  - `internal/vpntest`: the server counts the pings it receives (`Pings`) and sends one (`SendPing`).
- **OpenVPN files used as reference:** `ping.c` (`ping_string`, `check_ping_send_dowork`, `trigger_ping_timeout_signal`), `ping.h` (`check_ping_restart`, `check_ping_send`), `forward.c` (where the two timers are reset); `link-options.rst` for `--ping`, `--ping-restart` and `--keepalive`.

- **Tests (unit, under `testing/synctest`):** an idle session pings at 10, 20 and 30 seconds and not before (both links); a write every 6 seconds puts the ping off for 2 minutes and then it comes 10 seconds after the last write; pings from the server keep the session up for 10 minutes and are not given to `Read`; silence ends the session after 60 seconds, with `TagPingTimeout` (route and `timeout` metadata) from `Read` and `Write` as the same value, and the client pinged meanwhile; forged and replayed packets every 10 seconds do not keep it up; the options apply when nothing is pushed, what is pushed wins, zero is off for an hour; no goroutine left after `Close`; in the public package a `Conn` with `PingInterval` and `PingTimeout` ends with the exported tag; the config rows for negative values. For the read errors of a datagram link: 64 in a row are ignored and the packets after them arrive; an unbroken series of 65 ends the session with `TagLinkFailed` (op `read`, the cause kept); `net.ErrClosed`, `io.EOF` and `io.ErrClosedPipe` end it at once, on both links; a stream ends at its first error.

- **Learned:**
  - The plan wanted `TagPingTimeout` within 5 seconds of the death of the server; the first run gave `TagLinkFailed` ("connection refused") after 1 second over UDP: the ICMP error of a connected UDP socket was read as the end of the link. OpenVPN lets the keepalive decide, and so does this library now (SPEC §11.1, §21 O22). The platform-neutral rule (any error except a closed or ended link, and not 64 in a row) avoids a build tag for the Windows error.
  - A deterministic alternative to injecting the error with `ECONNREFUSED` itself: the tests use their own error, since the rule does not look at its type.

## Step 2.8: `Close`, exit, deadlines and the error contract (2026-11-22, tag `step-2.8`)

- **Built:**
  - `internal/session/exit.go`: `goodbye` (EXIT of the control channel with a bounded wait for its acknowledgement, or the OCC data packet, or nothing), the server's exit (`serverExited`: `io.EOF` after the handshake, `TagServerExit` before), the OCC exit bytes. `Close` is for one caller (`net.ErrClosed` for the others, at once); `Session.Done`/`Err` from step 2.7.
  - `internal/session/deadline.go` and `data.go`: `SetDeadline`, `SetReadDeadline`, `SetWriteDeadline`; `Read` and `Write` wait on the session, the deadline and the right to write (a channel of one place, so that a waiting `Write` can give up); the link write deadline is set only for the user's `Write`, under a lock that the loop's control writes also take.
  - Package `openvpn`: `Conn` is a `net.Conn` (`SetDeadline`, `SetReadDeadline`, `SetWriteDeadline`), `TagServerExit`, `IV_PROTO` bit 7 (1438) and the unexported `Config.noCCExit` knob.
  - `internal/vpntest`: the server counts the EXIT messages (`Exits`) and the data exit packets (`OCCExits`) it receives and sends the second (`SendOCCExit`).
- **OpenVPN files used as reference:** `sig.c` (`process_explicit_exit_notification_init` and its timer), `push.c` (`receive_exit_message`), `occ.c` and `occ.h` (`occ_magic`, `OCC_EXIT`), `multi.c` (what a server sends when it stops), `forward.c`.
- **Checks that ran:** `scripts/check.sh`. No new parser.
- **Tests (unit):** each row of the SPEC §5.3 table compared with `==`, in both link kinds, through `Conn`: `io.EOF` from `Read` after the server's `EXIT` (and from `Write`, and from a second `Read`), and `io.Copy(io.Discard, conn)` returning `nil` with the 6 bytes before it; `net.ErrClosed` from `Read`, `Write`, `Close`, the three deadline setters and `HandshakeContext` after `Close`; `os.ErrDeadlineExceeded` itself with `errors.As` to `net.Error` and `Timeout()`. In the session: `Close` sends `EXIT` once and does not wait when it is acknowledged; waits exactly one second when nothing is (a mute link); does not hang when the server is gone; sends one OCC packet on a datagram link and nothing on a stream when there is no `cc-exit`, and nothing before the handshake; a second `Close`, also during the first, is `net.ErrClosed`; the server's `EXIT` and OCC packet end the session with `io.EOF`, and an `EXIT` before the end of the handshake with `TagServerExit`; deadlines: a `Read` that waits gives up at the deadline (3 seconds exactly), a deadline in the past or moved wakes a `Read` in progress, an expired deadline wins over a waiting packet and the packet is still there afterwards, a `Write` after its deadline sends nothing, a link that does not take the packet gives a timeout and the session goes on, a stream cut in the middle of a frame ends the session with `TagLinkFailed`, a `Write` waiting for another is released by its deadline; 4 readers, 4 writers, a deadline changer and 5 `Close` calls at once under `-race`: one `Close` returns `nil`, all return, no goroutine is left.
- **Proof (the real server 2.7.9):** `TestCloseWithRealServer`: after `Close` the server logs `CC-EEN exit message received by peer` (UDP and TCP, `cc-exit`) or `OCC exit message received by peer` (UDP, the data channel exit) within 2 seconds, in fact at once (SPEC §21 O24). `TestServerStopWithRealServer`: a UDP server with `--explicit-exit-notify 1` sends `RESTART`, and the session ends with `TagServerRestart`; a TCP server's stop ends the session with `TagLinkFailed` (`EOF`).
- **Learned:**
  - The plan's "stopping the server gives `io.EOF`" is not what a real server does (SPEC §21 O23): a server in server mode never sends `EXIT`.
  - A deadline must not become a deadline of the link for everything that writes to it: the control packets of the loop would time out with the user's `Write`. The link deadline is the user's alone, under the lock of the link.
  - A `Write` that timed out in the middle of a TCP frame cannot be reported as a plain timeout: the stream has lost its framing.

- **Learned:**
  - A timer that is set to a time that the loop then tests with `After` instead of `!Before` spins forever in a test with a fake clock: the timer fires at exactly that time, the test says "not yet", the loop sets the timer again for now. Every time test in `renegTick` is `!now.Before(t)`.
  - The server pushes `dyn-tls-crypt` even when the first session has no protection (SPEC §21 O26), so the dynamic key is made for every session of this client; a test server that pushes the flag has to use the key too, or no renegotiation can happen.
  - The lame duck of OpenVPN is freed when the next renegotiation begins, not when the new key is made; a test server that kept it longer than the client kept its key would send packets that the client drops.
  - A failed renegotiation in OpenVPN throws away the whole TLS session; here only the failed state goes (SPEC §20 V11).
