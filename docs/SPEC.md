The sections that say "decided in step N" record what a step settled; the rest is the design.

This file is the source of truth. If the code and this file disagree, or a task needs a decision this file doesn't make, ask instead of guessing. When a decision changes, this file changes on the same branch.

## 1. Purpose and scope

`gopenvpn-conn` is a Go library that makes an OpenVPN client. A program gives it a configuration (a Go struct, or a `.ovpn` profile) and gets back a connection to an OpenVPN server that it uses with the types of the standard library.

It has three layers, each usable without the ones above it:

1. **The tunnel** (package `openvpn`, the module root): `*openvpn.Conn`, a `net.Conn` whose `Read` returns one IP packet from the VPN and whose `Write` sends one. No root, no change to the machine.
2. **The userspace network** (package `vpnnet`): `DialContext`, `Listen`, `ListenPacket` and a `*net.Resolver` over a tunnel, made by a TCP/IP stack inside the program. No root, no change to the machine. Only the connections of the program go through the VPN. `http.Transport{DialContext: n.DialContext}` is the usual use.
3. **The system tunnel** (package `tun`, after 1.0): a TUN device with the addresses and routes of the VPN, so that the whole machine uses it. Needs root or administrator rights.

and `ovpn`, the parser of `.ovpn` profiles.

**1.0 is a modern client** (the owner's decision, 2026-11-21):

| In 1.0 | Not in 1.0 (§22) |
|---|---|
| UDP and TCP to the server, IPv4 and IPv6 | HTTP and SOCKS proxies (a custom dial function can do it) |
| TLS 1.2 and 1.3 through `crypto/tls` | TLS below 1.2 |
| `tls-auth`, `tls-crypt`, `tls-crypt-v2`, and no control channel protection | |
| AES-128/192/256-GCM and CHACHA20-POLY1305, both AEAD packet formats (the 32-bit one and the epoch one) | CBC, CFB and OFB ciphers, `--auth` on the data channel |
| Cipher negotiation, keys from the TLS exporter | The old key derivation (servers before 2.6) |
| Certificates, `auth-user-pass`, `auth-token` | Challenge/response, `AUTH_PENDING` with web authentication, PKCS#11 |
| Pushed options, keepalive, renegotiation, exit notification | `PUSH_UPDATE`, compression, `fragment`, static-key mode, `--dev tap`, peer-to-peer mode |
| The tunnel, the userspace network and the profile parser, on Linux, Windows and macOS | The system tunnel (TUN) |

The reference server is OpenVPN 2.7.9, and a server from 2.6 on is expected to work.

- The constructors of `ControlWrap` take the contents of the key file (what a profile has inline): `NewTLSAuth(key []byte, direction KeyDirection, digest crypto.Hash) (ControlWrap, error)` with `KeyDirectionNone`, `KeyDirection0`, `KeyDirection1` and the digests SHA-1, SHA-256, SHA-384 and SHA-512; `NewTLSCrypt(key []byte) (ControlWrap, error)`; `NewTLSCryptV2(clientKey []byte) (ControlWrap, error)`. A `ControlWrap` holds a key and no connection state: every `Client` makes the protection of its own connection from it, so a `Config` is shared safely. `DefaultHandshakeTimeout` is 60 seconds. `Client` and `PacketClient` cannot return an error, so a `Config` that cannot be used (a negative timeout) makes the `Conn` fail at birth: `HandshakeContext` returns the error and `Close` closes the link.
- `Config.Credentials` is called once per connection, when the key exchange starts, with a context that ends with the connection (so a prompt can stop); it returns a `Credentials{Username, Password}`. The user name and the password travel in the key exchange message, which a server reads 2048 bytes of (§8.2): together with the peer info and the options string that leaves about 1400 bytes for the two, and credentials that do not fit end the handshake with `TagKeyExchangeTooLong` before anything of them is sent. A server may take less: an OpenVPN built without PKCS#11 takes 127 bytes of each and answers `AUTH_FAILED` (**changed after 1.0, §21 O33:** the client refused more than 127 bytes itself, which is the limit of that build only; a token of a login service is longer). `Config.MTU` is zero for 1500, and between 576 and 9000. `Config.PeerInfo` has names that start with `UV_` and have only letters, digits and underscores, values with no newline and no NUL, at most 32 variables, 64 bytes a name, 256 a value and 1024 bytes of all the lines together (so that the key exchange message stays inside what a server reads, with room for credentials). `DataCiphers` names are not case sensitive and are sent in capitals. A `Config` that breaks one of these makes the `Conn` fail at birth, with the invalid-config error that names the field in its metadata (`field`), and never a value.
- `Config.TLS` is required: a `Config` without it (and not built for the tests of the exchange of resets) makes the `Conn` fail at birth with the invalid-config error, because a client that does not verify the server is not made by accident. The library works on a copy of the `tls.Config` and raises a `MinVersion` below TLS 1.2 to TLS 1.2. `NewTLSConfig(TLSOptions{RootCAs, Certificates, RemoteCertTLSServer, MinVersion}) *tls.Config` builds the configuration of OpenVPN's profile options: the chain must lead to `RootCAs` (the system's when nil), the name in the certificate is not compared with the address, and with `RemoteCertTLSServer` the certificate must have a key usage extension and the extended key usage of a TLS server by name, as OpenVPN's `--remote-cert-tls server` asks (`options.c`: `remote_cert_ku[0] = OPENVPN_KU_REQUIRED`, `remote_cert_eku = "TLS Web Server Authentication"`; `ssl_verify_openssl.c x509_verify_cert_ku`, `x509_verify_cert_eku`); else `TagServerCertificateUsage`. **Fixed after 1.0 (§21 O32, a security fix):** the check was the one of `crypto/x509`, which takes a certificate with no extended key usage (or "any") as good for every use, so that in a PKI whose certificates have no usage, a client's certificate passed for the server's, which is what the option is there to stop. It sets `InsecureSkipVerify` only to turn off the name check of `crypto/tls`, and verifies the chain itself in `VerifyConnection`, which runs on every handshake. Later versions add `verify-x509-name` and the fingerprints to `TLSOptions`.
- **Added in step 3.2** for the options of profiles (`config.go`, `tlsconfig.go`): `Config.RetransmitTimeout`, `Config.AuthNoCache`, `Config.PullFilters` (`PullFilter{Action, Prefix}`, `PullAccept`, `PullIgnore`, `PullReject`; a rejected option ends the handshake with `TagPushedOptionRejected`, which carries the name of the option and never its arguments), `Config.RouteNoPull` (it takes out the pushed `route`, `route-ipv6`, `route-gateway`, `redirect-gateway`, `redirect-private`, `dhcp-option`, `dns` and `block-outside-dns`, the options that OpenVPN files under routes and DNS, `init.c` `pull_permission_mask`; a filter that matches first still decides), `Config.Validate` (the error that a `Conn` made with the `Config` would fail with, so a profile is checked when it is read), and in `TLSOptions`: `VerifyName` and `VerifyNameMatch` (`MatchSubject`, `MatchCommonName`, `MatchCommonNamePrefix`: `verify-x509-name`), `PeerFingerprints` (`peer-fingerprint`) and `CurvePreferences` (`tls-groups`). **`verify-x509-name`** is checked for the server's certificate after the chain: the subject is written as OpenSSL writes it for OpenVPN (the attributes in the order of the certificate, `short-name=value`, joined by `, `, a multi-valued part by ` + `, control characters as `\XX`), the common name is the last CN, a subject with a NUL byte is refused, and a prefix is a prefix of the common name; the tags are `TagServerNameMismatch` and `TagServerNameUnreadable`. **`peer-fingerprint`**: the server's certificate must have one of the SHA-256 fingerprints (`TagServerFingerprintMismatch`); with no `RootCAs` as well the chain is not verified, as in OpenVPN, and what is still checked is that the certificate is valid now and, with `RemoteCertTLSServer`, good for a TLS server (no extended key usage means any, as in `crypto/x509`); with `RootCAs` the chain is verified too.
- `network` is `"udp"`, `"udp4"`, `"udp6"`, `"tcp"`, `"tcp4"` or `"tcp6"`.
- `Dial` returns after the handshake: the tunnel is up and `ConnectionState` is complete. **A name with several addresses** (changed after 1.0, §21 O33): over TCP `net.Dialer` tries them until a connection is made. Over UDP no connection says that a server is there, and `net.Dialer` stops at the first address; so `Dial` looks the name up itself (the resolver of `NetDialer`) and tries the next address when the server at one sends nothing at all (a link that cannot be made, `TagServerPollTimeout`, an ICMP error, a handshake timeout with no packet), each address with `ServerPollTimeout` of its own, as OpenVPN does with the addresses of a remote (`init.c next_connection_entry`). A server that has answered is the server: its failure is returned and no other address is tried. The error is the last address's, with `addresses` and `addresses_tried` in its metadata. With `Dialer.DialContext` set the name goes to that function as it is. `Client` and `PacketClient` return at once; the handshake runs at `HandshakeContext` or at the first `Read` or `Write`, as with `tls.Conn`.
- One `Conn` is one session. Renegotiations happen inside it and the caller does not see them. When the session ends (the server says so, the keepalive times out, the link fails), `Read` and `Write` return the error and the caller dials again. A client that reconnects by itself is after 1.0 (§22).
- `Close` tells the server (§11.2), stops every goroutine of the connection and closes the link.

## 5. Standard library contracts

### 5.1 `*openvpn.Conn` as a `net.Conn`
- Message semantics, like a connected `*net.UDPConn`: one `Read` is one IP packet. A buffer that is too small gets the start of the packet and the rest is dropped; `ConnectionState().MTU` is the size that is always enough. One `Write` is one IP packet; a packet larger than the MTU is an error.
- `Read`, `Write` and `Close` may be called from different goroutines at the same time. Deadlines behave as `net.Conn` says, and a deadline in the past unblocks a call in progress.
- The data channel is unreliable: `Write` returning `nil` does not mean the packet arrived.

### 5.2 Context
A context that is done stops `Dial`, `HandshakeContext` and the dial functions of `vpnnet`. The context of a dial does not bound the life of the connection.

### 5.3 Errors of the contracts (D2)
The owner's error package tags every error (§14). Three values are the exception, because callers and the standard library compare them with `==` or assert `net.Error` (`io.Copy` and `io.ReadAll` stop on `err == io.EOF`; `net/http` asserts `err.(net.Error)` for timeouts):

| Value, returned untouched | When |
|---|---|
| `io.EOF` | `Read`, after the server ended the session with `EXIT` |
| `net.ErrClosed` | Any method after `Close` |
| `os.ErrDeadlineExceeded` | `Read` or `Write` when its deadline passes |

The connections and listeners that `vpnnet` returns (`net.Conn`, `net.Listener`, `net.PacketConn`) are gVisor's `gonet` types and return what `gonet` returns (`*net.OpError` and the like) from their methods, untouched, for the same reason; the lookups of `Resolver` return the `*net.DNSError` of the standard library. The functions of `vpnnet` that make them (`New`, `DialContext`, `Listen`, `ListenPacket`) return tagged errors, except `net.ErrClosed` after `Close` (and the error that ended the `Conn` after the tunnel ended). Every other error of the module is a tagged `*errors.Error`, and `errors.Is` still finds a cause such as `context.Canceled` through it.

## 6. Link and framing

- Source: `socket.c`; Draft "OpenVPN wire packet format".
- UDP: one datagram is one packet. TCP: each packet has a 16-bit length before it, in network byte order.
- The first byte is the opcode (the high 5 bits) and the key id (the low 3 bits).
- A packet that is too short, too long or has an unknown opcode is dropped and counted; it never ends the session (anyone can send one).
- The largest control packet is 1250 bytes (`TLS_MTU_DEFAULT`, `--max-packet-size`).

## 7. Control channel

### 7.1 Protection (`internal/ctrlwrap`; source `tls_crypt.c`, `ssl_pkt.c`, `packet_id.c`)
- **None:** the plain control packet.
- **`tls-auth`:** an HMAC (SHA-1 by default; SHA-256, SHA-512 by `--auth`) over the pseudo packet of the draft, with a 64-bit replay id (packet id, then time). `key-direction` selects the keys.
- **`tls-crypt`:** HMAC-SHA256 as a synthetic IV and AES-256-CTR, with the same replay id.
- **`tls-crypt-v2`:** `tls-crypt` with the client key `Kc`; the wrapped key `WKc` is appended to `CONTROL_HARD_RESET_CLIENT_V3` and, when the server asks with the early negotiation flag, to `CONTROL_WKC_V1`.
- **Dynamic `tls-crypt`** (`protocol-flags dyn-tls-crypt`): renegotiations use a key from the TLS exporter (`EXPORTER-OpenVPN-dynamic-tls-crypt`).
  - **Decided in step 2.9** (`internal/ctrlwrap/dynamic.go`, `internal/session/renegotiate.go`; source `tls_crypt.c` `tls_session_generate_dynamic_tls_crypt_key`, `xor_key2`, `ssl.c` `tls_session_update_crypto_params_do_work`, `ssl_pkt.h` `tls_session_get_tls_wrap`): the key is made once, from the TLS session of key id 0, when the push reply is complete: 256 bytes from the exporter with the label above and no context, laid out like a static key (two keys of 128 bytes). Whatever protected the first session, `tls-auth` and `tls-crypt` (and `Kc` of `tls-crypt-v2`) alike, the exported bytes are XORed byte by byte with the 256 bytes of that static key; with no protection they are used as they are. The result is the key of a `tls-crypt` wrapper (so `tls-auth` turns into `tls-crypt`), used by the client with the inverse direction and by the server with the normal one, with a replay counter of its own that starts fresh. It protects every control packet with a key id above 0, in both directions, the soft resets included (the packets that start a renegotiation are wrapped with it too); key id 0 keeps its own wrapper for as long as it lives. One wrapper serves all the renegotiations of the session. The client offers it with `IV_PROTO` bit 9 and uses it when the server pushes `dyn-tls-crypt`; a server that does not push it leaves the static wrapper for all key ids.
- A packet is authenticated first; its replay id is checked next; only then is anything in it used. A packet that fails is dropped silently.

### 7.2 Reliability (`internal/reliable`; source `reliable.c`, `ssl.c`)
- Each control packet has a 32-bit id, starting at 0, with no gaps; a retransmission keeps its id. Acks are single ids, up to 8 in a packet, sent in `ACK_V1` or on other packets.
- The numbers the peer depends on are OpenVPN's: 6 packets in the send window, 12 in the receive window. The retransmission starts from OpenVPN's timing: after 2 seconds (`--tls-timeout`), doubling each time up to 128 seconds, and at once when three later packets were acked.
- TLS bytes are cut into control packets so that no packet is larger than the limit of §6.
- Acknowledgements: a received packet is acknowledged when it is new and less than 12 ahead of the next expected id, and also when it is a copy of one already taken (its acknowledgement may have been lost). A packet more than 11 ahead, or one that arrives when 8 acknowledgements wait unsent, is dropped without an acknowledgement; the peer sends it again. Each outgoing packet repeats the most recently acknowledged ids while there is room (up to 8), as OpenVPN does.
- Ids are compared with serial number arithmetic. A hard reset must have id 0 (the session checks that; the layer does not know opcodes).

### 7.3 Handshake (source `ssl.c`, `ssl_pkt.c`, `session_id.c`)
1. The client sends `CONTROL_HARD_RESET_CLIENT_V2` (`V3` with `tls-crypt-v2`) with a random 64-bit session id.
2. The server answers `CONTROL_HARD_RESET_SERVER_V2` with its session id.
3. The client acks, and TLS starts in `CONTROL_V1` packets.

The handshake has `HandshakeTimeout` to finish, pushed options included. With `Config.ServerPollTimeout` the server must also answer within that time (`Dial`: the link is made and the first packet of the server comes; else `TagDialFailed` or `TagServerPollTimeout`); once it has answered, that timeout bounds nothing more (OpenVPN: `forward.c check_server_poll_timeout`).

Until TLS runs (step 1.11) the handshake is complete when the server's reset has arrived and been acknowledged and the client's reset has been acknowledged. With `tls-crypt-v2`, when the server's reset asks for the wrapped key, the acknowledgement travels in an empty `CONTROL_WKC_V1` (packet id 1); step 1.11 replaces that empty packet with the first bytes of TLS. The real server answers the first reset without keeping state (§21 O7), so the third packet is what makes it start a session: in the finished client that packet is the TLS ClientHello, which is a reliable packet and is sent again until it is acknowledged.
- The reader goroutine passes each packet to the loop in a slice of its own (the packets of the control channel are small and rare; the data channel has its own path, §10). A packet of the wrong protection, from another session, of an opcode that a server does not send, with a key id other than 0, or of no use yet, is dropped and counted, never answered (§15 rule 7).

## 8. TLS, key exchange and negotiation

### 8.1 TLS (source `ssl.c`, `ssl_verify.c`; `crypto/tls` does the work)
- `crypto/tls` runs as a client over an internal `net.Conn` that the reliability layer feeds. TLS 1.2 (with Extended Master Secret) and 1.3.
- The caller's `tls.Config` decides the verification. The profile parser builds it for `ca`, `cert`, `key`, `remote-cert-tls server`, `verify-x509-name`, `peer-fingerprint`, `tls-version-min`, `tls-groups` (§12).
- The TLS bytes go in `CONTROL_V1` packets, in order. A packet carries at most `1250 - 48 - 1 - 8 - 41 - 4 - <protection overhead>` bytes (OpenVPN's `tls_mtu` of 1250, the IPv6 and UDP headers, the first byte, the session id, the room for 8 acknowledgements, the packet id): 1108 with `tls-crypt`. The first packet that follows the server's reset is a `CONTROL_WKC_V1` when the server asked for the wrapped key (§7.1), and then carries `max(16, that - len(WKc))` bytes. The packets are cut as the send window of 6 has room: what `crypto/tls` writes waits in the loop until then, and the next write is not taken before that.
- The client's TLS runs in a goroutine of its own (`tlsMain`) over an internal `net.Conn` whose `Write` hands the bytes to the loop and whose `Read` returns the bytes that arrived in order. At most 256 KiB of TLS may wait to be read: a packet that would pass the limit is not acknowledged, so the server sends it again when TLS has caught up (§15 rule 6). The TLS goroutine ends when the handshake does, and when the session ends.
- After the handshake, each control message is one TLS record of plain text ending with a NUL byte.

### 8.2 Key exchange (`internal/ctrlmsg`; source `ssl.c` key method 2, `ssl_util.c`)
- The client sends the key method 2 message: random bytes, the options string, the user name and password (when `Credentials` is set), and the peer info.
- Peer info: `IV_VER`, `IV_PLAT`, `IV_PROTO`, `IV_CIPHERS`, `IV_MTU`, and the `UV_` variables of the configuration. `IV_PROTO` has the bits of what is implemented: 1 (`DATA_V2`), 2 (push without request), 3 (TLS exporter), 4 (`AUTH_PENDING` keywords), 7 (exit in the control channel), 8 (`AUTH_FAILED,TEMP`), 9 (dynamic `tls-crypt`), 10 (epoch format), 11 (`dns` option). A bit is added in the step that implements it, not before. Implemented so far: 1, 2, 3, 4, 7, 8, 9 and 10 (`IV_PROTO` is 1950).
- **Decided in step 2.1** (§21 O16): `IV_VER=gopenvpn-conn <version>` (for example `gopenvpn-conn 0.2.0`; the server turns the space into an underscore for its scripts and reads nothing else of it) and `IV_PLAT=linux`, `win` or `mac`. The server uses neither to choose a protocol. `IV_MTU` is the larger of 1600 (OpenVPN's default) and the tunnel MTU. The other lines are `IV_TCPNL=1`, `IV_NCP=2` (when AES-128-GCM and AES-256-GCM are both offered), `IV_CIPHERS` and `IV_PROTO`, then the `UV_` variables in order of name.
- The options string is built from the configuration in the form of OpenVPN's client, `V4,dev-type tun,link-mtu <mtu+41 or +43 for TCP>,tun-mtu <mtu>,proto <UDPv4|UDPv6|TCPv4_CLIENT|TCPv6_CLIENT>,cipher <first data cipher>,auth [null-digest],keysize <bits>,key-method 2,tls-client`, at most 511 bytes. The server compares it with what it expects and only warns (§20 V1).
- Each control message is written to TLS in one `Write`, and the server's message is read with one `Read`: a message is one TLS record, as OpenVPN reads it. For that the library turns off the dynamic record sizing of `crypto/tls` (`DynamicRecordSizingDisabled` on its copy of the `tls.Config`), which otherwise cuts the first writes of a connection into records of about 1200 bytes (§21 O33). The key exchange message is at most 2048 bytes (`MaxKeyExchangeLen`, OpenVPN's `TLS_CHANNEL_BUF_SIZE`: the buffer that a server reads the cleartext into, and that OpenVPN's client writes from); a longer one is refused with `TagKeyExchangeTooLong`. A user name or a password is at most 4095 bytes (`USER_PASS_LEN` of a build with PKCS#11), which the 2048 bytes of the message bound first. The random fields are from `crypto/rand`. The password is cleared from the message buffer after the write; the strings that `Credentials` returned cannot be cleared.

### 8.3 Negotiation (source `ssl_ncp.c`, `push.c`, `options.c`)
- The server picks the data cipher from `IV_CIPHERS` and pushes it with `cipher`. A cipher that was not offered ends the handshake.
- **D3.** The data keys come from the TLS exporter (`EXPORTER-OpenVPN-datakeys`, 256 bytes; RFC 5705, RFC 8446 §7.5), when the server pushes `key-derivation tls-ekm` or `protocol-flags tls-ekm`. A server that does not is refused in 1.0 with its own tag (§22 has the old derivation).
- `protocol-flags` also turns on `cc-exit`, `dyn-tls-crypt` and `aead-epoch`.

## 9. Pushed options (`internal/ctrlmsg`; source `push.c`, `push_util.c`, `options.c`)

- The client sends `PUSH_REQUEST` at once and repeats it every 5 seconds until the reply is complete; it also announces "push before request" (`IV_PROTO` bit 2), so the server usually answers first. A reply may come in several parts: every part but the last ends with `push-continuation 2`. At most 4096 options are taken over all the parts; a PUSH_REPLY that is longer ends the handshake. `HandshakeContext` returns when the last part has been processed.
- A control message is text and a NUL. The reader ends a message at the NUL, whatever the TLS records are: OpenVPN's servers send one message in one record, but `crypto/tls` cuts a long write into records, and a message of 64 KB or more without a NUL ends the session (`TagControlChannelFailed` is for the TLS session that ends; the too long message has its own unexported tag). Messages that are not yet understood are ignored and logged by name only.
- Each pushed option is in one of three groups, and the tables are in the code with a test per option:
  - **Used:** `ifconfig`, `ifconfig-ipv6`, `route`, `route-ipv6`, `route-gateway`, `redirect-gateway`, `topology`, `dhcp-option DNS`/`DNS6`/`DOMAIN`/`DOMAIN-SEARCH`, `dns`, `tun-mtu`, `ping`, `ping-restart` and `ping-exit` (one timer in OpenVPN, `ping_rec_timeout`, with another thing to do at its end; here both end the session with `TagPingTimeout`, and the later one of a reply counts; **changed after 1.0:** `ping-exit` was ignored, so a server that pushes it and no `ping-restart` left the client without a timeout), `peer-id`, `cipher`, `key-derivation`, `protocol-flags`, `auth-token`, `auth-token-user`, `reneg-sec`, `explicit-exit-notify`.
  - **Ignored, kept in `PushedOptions`:** options that only matter to a system tunnel or to OpenVPN's own program (`block-outside-dns`, `register-dns`, `persist-tun`, `sndbuf`, `rcvbuf`, ...).
  - **Refused, ending the handshake with `TagUnsupportedPushedOption`:** options that change the packet format in a way 1.0 does not implement: `compress` or `comp-lzo` with anything that adds framing, `fragment`, a cipher that is not AEAD.
- **An option that cannot be read is left out, not fatal** (the audit after 1.0, §21 O32): OpenVPN's errors of pushed options are not fatal (`options_parse.c apply_push_options`, `D_PUSH_ERRORS` is `M_NONFATAL`), and a route or a DNS server less is no reason to have no tunnel. So a `route`, `route-ipv6`, `route-gateway`, `dhcp-option`, `dns`, `ping`, `ping-restart`, `reneg-sec` or `explicit-exit-notify` that does not parse is skipped, logged at `Warn`, and listed in `Pushed.Skipped` with what was wrong; `route` with a keyword for its network (`remote_host`, `net_gateway`, `vpn_gateway`: the route that sends the packets for the server past the VPN, which real servers push) is one of them, because it is a route of the host. Only the options that the tunnel cannot do without still end the handshake when they cannot be read (`tagBadPushedOption`): `topology`, `ifconfig`, `ifconfig-ipv6`, `tun-mtu`, `peer-id`, `cipher`, `key-derivation`, `auth-token`, `auth-token-user`. `explicit-exit-notify 0` is a value.
- An unknown option is ignored, logged at `Warn` by name, and kept in `PushedOptions`. The value of `auth-token` is the exception to "as received": it is a secret, so `PushedOptions` has the word only (§20 V7).
- A pushed `cipher` must be AEAD and supported (AES-128-GCM, AES-192-GCM, AES-256-GCM, CHACHA20-POLY1305), else `TagUnsupportedPushedOption`; and it must be one the client offered, else `TagCipherNegotiationFailed` (metadata `cipher`). `compress` (with any argument or none), `comp-lzo` (with any) and `fragment` are refused; so are malformed arguments, with an unexported tag that names the option. The arguments are split at spaces (no quotes), the options at commas.
- `ifconfig` is two words: with `topology subnet` an address and a netmask, with `net30` (the default when none is pushed) and `p2p` the local and the remote address; the length of the tunnel address is 24 (or whatever the mask says), 30 and 32. `route` takes a network, a netmask, a gateway and a metric; the keywords `default`, `vpn_gateway`, `net_gateway` and `remote_host` are understood (the last two leave the gateway empty).
- `AUTH_FAILED` (with `TEMP` and its `backoff` and `advance` keywords in the metadata), `HALT` and `RESTART` end the session with their tags (§14.3). `AUTH_PENDING` extends the wait up to its `timeout`, within the context of the handshake. **Decided in step 2.3:** the timeout counts from the start of the handshake and never shortens it; one without a time keeps `HandshakeTimeout`; it is cut to the longer of `HandshakeTimeout` and 30 minutes (OpenVPN allows its renegotiation time, an hour by default, but a server that holds a client for an hour in a handshake is not a case of this library); one that comes after the handshake is complete is ignored. These messages are read before the push reply logic and end the session whenever they arrive, during the handshake or after it (§14.2).

## 10. Data channel (`internal/datachan`; source `crypto.c`, `crypto_epoch.c`, `packet_id.c`, `forward.c`)

- **Packets:** `DATA_V2` (opcode, key id, 24-bit peer id) when the server pushed `peer-id`; `DATA_V1` otherwise.
- **AEAD format** (Draft "AEAD encrypted data channel packet"): 32-bit packet id, 16-byte tag before the ciphertext, nonce = packet id then the implicit IV from the key material, the header as additional data.
- **Epoch format** (`aead-epoch`; Draft "... with extended packet id and epoch keys"; `crypto_epoch.c`): 64-bit packet id (16 bits of epoch, 48 of counter), tag at the end, nonce = implicit IV XOR packet id, a new key for each epoch from `OVPN-Expand-Label` (HKDF-SHA256), with OpenVPN's usage limits for AES-GCM and its window of future epochs.
- **Replay protection** (`internal/replay`): OpenVPN's sliding window (64 packets, 15 seconds by default), for UDP and TCP alike: OpenVPN's `replay_window` does not depend on the protocol, and its mode without a window is only for `--replay-window 0` (§21 O31). A replayed, late or unauthenticated packet is dropped and counted.
- **Never a repeated nonce:** before a packet id can wrap, the session renegotiates (32-bit format) or moves to the next epoch (epoch format); if neither is possible in time, the connection ends with a tag rather than send.
- **Key slots** (`ssl.c`, `ssl_common.h`): the active key, the retiring key (decryption only) and the next key during a renegotiation, selected by the key id of the packet.
- The payload is an IP packet with no extra framing (compression is refused, §9).
- **Decided in step 2.4** (`internal/datachan`, `internal/keys/datakeys.go`):
  - The 256 bytes of exporter material are cut in four parts of 64: cipher key and second key client to server, then server to client. The library is always the TLS client: it seals with the first pair and opens with the second. Only the first 16, 24 or 32 bytes of the cipher key are used, and the first 8 bytes of the second key are the implicit IV.
  - `Seal` and `Open` allocate nothing when the caller's buffers have room (the receiver keeps one scratch buffer for the ciphertext and tag in the order Go's AEAD wants, because the packet has the tag first). The sender's ids start at 1; `NeedsRenegotiation` is true from `0xFF000000` (OpenVPN's `PACKET_ID_WRAP_TRIGGER`), and when the last id has been used `Seal` returns `TagPacketIDExhausted` and never repeats one.
  - **Decided in step 2.10** (`internal/session/bufpool.go`): the packets of the data channel that go from the reader to the loop and from the loop to `Read` travel in buffers of a pool that belongs to the session (a control packet is kept by the reliability layer and gets a buffer of its own), so `Conn.Write` and `Conn.Read` allocate nothing per packet in steady state (`BenchmarkWrite`, `BenchmarkRead`: 0 allocations, 1400-byte packets, both formats). A buffer is given back as soon as the loop has opened the packet and as soon as `Read` has copied it; the pool grows to the largest packet that came.
  - The receiver checks the replay window before it decrypts (a cheap refusal that changes nothing) and records the id after the packet authenticated. A stream link has the same window as a datagram link: a server with the kernel data channel drops packets on a TCP link when its socket is full, so ids can be missing there too (§21 O31; until step 5.1 a stream link took strict order, each id the last plus one, and a download through such a server stalled). The peer id of a received `DATA_V2` packet is authenticated (it is in the additional data) but not compared: the server writes the id that it uses for the client and OpenVPN's client does not compare it either.
  - Every refusal is an error with its own tag, none of them ends a session; the receiver also counts them by reason (`Dropped`).
  - The AEAD cipher names are the four of §9, compared without regard to case (OpenVPN does the same).
- **Decided in step 2.6** (`internal/keys/epoch.go`, `internal/datachan/epoch.go`):
  - The epoch format is used when the pushed `protocol-flags` has `aead-epoch` (the client announces it with `IV_PROTO` bit 10); it exists only for `DATA_V2`, so a server that pushes it with no `peer-id` ends the session (`DataEpochNeedsPeerID`). `datachan.Channel` (`Seal`, `Open`, `NeedsRenegotiation`, `Dropped`) is the interface of both formats; the session holds one.
  - The key of epoch 1 of each direction is the first 32 bytes of that direction's cipher key; `ExpandLabel` is OVPN-Expand-Label (`crypto/hkdf` with SHA-256); the data key and the 12-byte implicit IV of an epoch come from `data_key` and `data_iv`, the next epoch from `datakey upd`. The known answers of OpenVPN's `test_crypto.c` (the label expansion and `epoch_test_derive_data_key`) are in the tests of `internal/keys`.
  - Sender: the counter of an epoch starts at 1; before each packet the epoch moves on when `blocks + counter` of the key passes the usage limit (2^36 - 1 for AES-GCM, none for CHACHA20-POLY1305), when the receive key has passed it while the two epochs are equal (this pushes the peer to a new epoch too), or when the 48-bit counter is used up; at epoch 0xffff with the counter used up `Seal` returns `TagPacketIDExhausted`. The blocks counted are those of the packet id and the payload, as OpenVPN counts them. `NeedsRenegotiation` is true from the send epoch `0xF000`.
  - Receiver: the current key, the retiring one (with its replay window) and `DefaultFutureKeys` = 4 keys of the epochs after the current one (OpenVPN 2.7.9 and the draft; earlier OpenVPN kept 16). An epoch of 0, beyond the future keys, or in the last `FutureKeys + 1` epochs below 0xffff (whose future keys would run past it) has no key and the packet is dropped (`DataPacketUnknownEpoch`). The replay window is per epoch. A packet of a future epoch moves the receiver there only after it authenticated, and then the sender is moved to that epoch too if it is behind (the draft says SHOULD; OpenVPN does it).
  - A test-only usage limit (`EpochOptions.UsageLimit`, and `Config`'s unexported `epochUsageLimit`) makes a channel go through many epochs with a few packets; and an unexported `Config.noEpoch` makes the client not announce the format, so that the real-server tests also go through the 32-bit format.
- **Decided in step 2.5** (`internal/session/data.go`):
  - The data channel is made when the push reply is complete, before the handshake is: the keys come from the exporter of the TLS session, the cipher is the pushed one, and the header has the pushed peer id (`DATA_V2`) or none (`DATA_V1`), key id 0. A data packet that comes before that (the server may send one right after its reply) is dropped and counted, as a lost packet would be. A server that does not push `key-derivation tls-ekm` (or the flag) ends the handshake with `TagKeyDerivationUnsupported`; an exporter that fails (TLS 1.2 without the extended master secret) with `TagKeyExportFailed`; no pushed cipher, with `TagCipherNegotiationFailed`.
  - The loop goroutine opens the packets and puts each IP packet in a queue of 512 for `Read`; when the queue is full the packet is dropped and counted (the loop also runs the control channel, so it never waits for a reader). `Write` seals under a mutex and writes the link itself, one `Write` of the link for each packet (and each TCP frame), so ids and the stream stay in order; it never touches the loop. A packet that is not an IP packet, the 16-byte ping, is not given to `Read` (step 2.7 answers it).
  - `Write` refuses an empty packet and one larger than the MTU (`TagPacketTooLarge`; the pushed `tun-mtu`, else `Config.MTU`, else 1500) without ending the session. The end of the packet ids (`TagPacketIDExhausted`) ends it, and so does a failure of a stream link: the error is made where it happens, stored, and every later call returns it. A failed write of a datagram link does not (§11.1).
  - Both links take the window of §10 (§21 O31).
- **The MSS clamp** (decided after 1.0, §21 O34; `internal/mss`, `internal/session/data.go`; source `mss.c mss_fixup_ipv4`, `mss_fixup_ipv6`, `mss_fixup_dowork`, `frame_calculate_mssfix`, `options.c` mssfix): the `Conn` lowers the MSS option of every TCP SYN that it reads (after the packet opened) and writes (before it is sealed), as OpenVPN's client does for both directions, so that a full segment of a TCP connection in the tunnel, in its OpenVPN packet, fits in one packet of the network under it. A server with the kernel data channel does not clamp (`dco_linux.c dco_set_peer` does not pass `mssfix` to the kernel), so without this the segments travel as IP fragments, which networks drop. Every user of the `Conn` gets it: `vpnnet`, and a program that wires the `Conn` to a real TUN.
  - **The limit** is OpenVPN's, with the numbers of this session: for a size S counted as a packet (`MSSFixPacket`), MSS = S - overhead - 40; counted with the link's headers (`MSSFixMTU`), S - encap - overhead - 40, where encap is 8 for UDP or 20 for TCP plus 20 for IPv4 or 40 for IPv6 (from the address of the link); fixed (`MSSFixFixed`), S - 40. The overhead is that of the data packet: the opcode with the peer id (4 for `DATA_V2`, 1 for `DATA_V1`), the packet id (4, or 8 in the epoch format), the tag (16), and 2 for the length on a stream link. Every cipher is AEAD, so there is no rounding to a block size. A SYN over IPv6 gets 20 less.
  - **The default** is OpenVPN's: `mssfix 1492 mtu` when the MTU is 1500 (`MSSFixFixed` alone makes it 1492 fixed), else the MTU, fixed. On UDP over IPv4 with `DATA_V2` that is an MSS of 1400 (1396 in the epoch format), on TCP 1386; the IP packets on the network are then at most 1492 bytes. `ConnectionState.MSS` says what is in use; it is fixed when the data channel is made (the pushed `peer-id` and `protocol-flags` count).
  - **Which packets:** a whole TCP packet (the IPv4 total length or the IPv6 payload length is the packet's) with SYN set, not a fragment, over IPv4 with a header of at least 20 bytes (§20 V14), or over IPv6 with TCP as the first next header. Every well-formed MSS option (kind 2, length 4) above the limit is lowered, and the TCP checksum is changed by RFC 1624 eq. 3; an option list that runs past the header ends the walk. Nothing else is touched. `Write` clamps a copy in a buffer of the session, never the caller's slice (the `io.Writer` contract); `Read` clamps the packet in the session's buffer before it is copied out.

## 11. Keepalive, exit, renegotiation

### 11.1 Keepalive (source `ping.c`, `forward.c`)
- When nothing was sent for `PingInterval`, the client sends the 16-byte ping packet on the data channel. A received ping is not given to `Read`.
- When nothing was received for `PingTimeout`, the session ends with `TagPingTimeout`.
- **Decided in step 2.7** (`internal/session/keepalive.go`; source `ping.c`, `ping.h`, `forward.c`):
  - The values are the pushed `ping` and `ping-restart` when there are any, else `Config.PingInterval` and `Config.PingTimeout`; zero is off, negative is an invalid config. Both timers start when the handshake is complete.
  - **Idle** is "no packet went to the link": any packet counts, a control packet too, and the ping itself. **Silence** is "nothing authentic came": a control packet that passed its protection and session checks (an `ACK_V1` too), and a data packet that opened, the ping included, which `Read` does not get. A forged, replayed or foreign packet counts for neither.
  - The loop owns the timers and sends the ping itself (through the same sealing as `Write`, under its mutex); `Write` only stamps the time of the last send, so a busy tunnel never wakes the loop for the ping.
  - `ConnectionState.PingInterval` and `PingTimeout` stay the pushed values (zero when none).
  - **A read error of a datagram link does not end the session.** A connected UDP socket returns the ICMP "port unreachable" of an earlier packet as the error of a later read (`ECONNREFUSED`; a reset on Windows), which says nothing about the packets to come, and OpenVPN lets the keepalive decide. So the session goes on after any such error, unless the link is closed or at its end (`net.ErrClosed`, `io.EOF`, `io.ErrClosedPipe`) or it gives 64 errors in a row with no packet between (a socket that is broken for good). A stream link has no such errors: its first error ends the session.
  - **A write error of a datagram link does not end the session either** (the audit after 1.0, §21 O32; `internal/session/linkwrite.go`). OpenVPN only logs a failed write (`forward.c process_outgoing_link`, `error.c x_check_status`) and lets the keepalive decide; the errors are everyday ones: the ICMP error of an earlier packet returned to the next `sendto` (`ECONNREFUSED`), a route that is gone for a moment (`ENETUNREACH`), a full interface queue (`ENOBUFS` on macOS), a firewall (`EPERM`), a packet too large for the path (`EMSGSIZE`). The packet is lost, `Write` returns as if it was sent, and the session goes on. It ends (`TagLinkFailed`) when the link is closed, when a write fails before the server has ever answered (so a dial fails at once and the next remote is tried; OpenVPN restarts there too), and, with no keepalive timeout to decide, when every write has failed for 120 seconds (OpenVPN's ping-restart before the push).
  - **The loop never waits for the link** (the audit after 1.0). The control packets and the pings of the loop go to a goroutine that writes them (`writeLoop`, a queue of 64; a packet that does not fit is dropped: the reliability layer sends it again), so a stream link that takes no more bytes (a TCP connection whose path died during an upload, a peer that does not read) does not stop the timers: the keepalive timeout still ends the session, incoming packets are still read, and `Close` returns. A ping is not sent while a `Write` of the connection holds the data path (its packet is going out, or waits as the ping would). A write deadline that is set while a `Write` waits in the link reaches the link (`SetWriteDeadline` wakes it). After `Close` (not after a failure) the writer still sends what the loop gave it, for at most a second, under a write deadline on the link. Before this, the loop wrote to the link itself and waited behind a blocked `Write`: the session then hung until the kernel gave the TCP connection up (about 15 minutes on Linux), and `Close` with it.
  - **A ping that is overdue is due now** (the audit after 1.0): the wait of the keepalive timer was the time left of the timeout whenever the ping was overdue, so a loop that woke just after the ping was due (a packet arrived) sent no ping until the application wrote, and the server gave the client up after its own timeout, on a healthy link. `keepaliveWait` now returns 0 for an overdue ping. The timeout is not taken while packets wait to be looked at.

### 11.2 Exit (source `sig.c`, `ssl.c`, `occ.c`)
- `Close` sends `EXIT` in the control channel when `cc-exit` was negotiated; otherwise, over UDP, the older exit notification of `--explicit-exit-notify` on the data channel. Then it closes, without waiting for an answer for longer than a short bound.
- `EXIT` from the server ends the session cleanly: `Read` returns `io.EOF`.
- **Decided in step 2.8** (`internal/session/exit.go`, `deadline.go`, `data.go`):
  - The client announces `IV_PROTO` bit 7 (1438 then, 1950 since step 2.9), so a server that supports it pushes `protocol-flags cc-exit`. `Close` then writes `EXIT` to the control channel and waits up to 1 second for its acknowledgement (the loop sends it again meanwhile). **While a renegotiation is under way** `EXIT` waits for the new key, inside the same second (changed after 1.0, §21 O33): the server reads the control messages of the newest key only, from the moment that the renegotiation began (`ssl.c tls_process` works on the primary key), so an `EXIT` in the TLS session of the key before it was never read, and the server kept the client until its ping timeout; OpenVPN's client keeps what it has to send until the new key is active (`ssl.c tls_send_payload`). When the renegotiation does not finish in that second nothing is sent; without `cc-exit`, over a datagram link, it sends the data packet of the older notification once (OpenVPN's default is one try); over a stream it sends nothing. The server's `EXIT` (control) and the same OCC packet (data) end the session with `io.EOF`; before the handshake is complete they end it with the tagged `TagServerExit`. `Close` before the handshake says nothing. Failing to say goodbye is only logged.
  - `Close` is for one caller: a second call, even while the first still waits, returns `net.ErrClosed` at once, and so do the deadline setters from the moment `Close` starts.
  - A session that ended with `io.EOF` returns it from `Write` too (every later call returns the value that ended the session, §14.2).
  - **Deadlines** follow `net.Conn`. `Read` and `Write` return `os.ErrDeadlineExceeded` itself when the time has passed, before they look at a waiting packet; a deadline that is changed or is in the past wakes the calls that wait; zero turns it off. They start no goroutine and no timer of their own: each waiting call makes its timer. They bound the wait for a packet, for the right to write (one `Write` at a time seals and sends, and a waiting one can give up) and for the link, not the handshake that a first `Read` or `Write` may start (`HandshakeTimeout` does). A `Write` whose deadline passes inside the link sets the write deadline of the link only for itself (the loop's control packets wait for it, and never get the deadline); on a datagram link, or a stream where nothing of the frame was written, the session goes on, and on a stream that wrote a part of the frame it ends with `TagLinkFailed`, as a stream that lost its framing cannot go on.

### 11.3 Renegotiation (source `ssl.c`)
- Either side starts it with `CONTROL_SOFT_RESET_V1`; a new TLS session runs under the next key id (1 to 7, then 1 again), the key exchange of §8.2 is repeated with the auth token instead of the password when the server pushed one, and new data keys are made.
- It starts after `RenegotiateAfter`, or earlier when the packet id or the AEAD usage limit asks for it.
- The new key becomes the active one after OpenVPN's delay, and the old one stays for decryption during the transition. A renegotiation that fails ends the session with a tag (the caller dials again): a real server takes no second try in the same session (§20 V11, changed after 1.0).
- **Decided in step 2.9** (`internal/session/keystate.go`, `renegotiate.go`; source `ssl.c` `key_state_soft_reset`, `tls_process`, `should_trigger_renegotiation`, `lame_duck_must_die`, `auth_deferred_expire_window`, `tls_select_encryption_key`):
  - **Key states.** A session has one control channel state for each key id that is alive (`keyState`): its own reliability layer (packet ids from 0), its own TLS session, its own data keys. The session ids belong to the session, not to a key state, so a soft reset carries the same ones. The client is the TLS client in every key state, whoever started the renegotiation. A packet is routed by the key id in its first byte; one for a key id that has no state is dropped, and so is one that opens a state without being a soft reset.
  - **Starting.** Both sides send their own `SOFT_RESET_V1` (id 0) as the first packet of the new key state; the TLS handshake starts when the other's soft reset has arrived (as after the hard reset of key id 0). A soft reset of a key id that is free is accepted only after it is authenticated (with the wrapper of §7.1 for that key id), only while the newest key is complete (OpenVPN's `ks->state >= S_GENERATED_KEYS`), and a reset of key id 0, a hard reset of another id, and a reset with a packet id other than 0 are dropped. When the soft reset is of the key id that the client has started itself (both start together), it is the answer and no second renegotiation begins. The key id counter of the session is the next one after the last started, 7 being followed by 1; a soft reset of the server's makes the client continue from its id.
  - **Two keys.** At most two keys carry data: the newest and the one before it. When a renegotiation begins, the key before the newest is thrown away at once (OpenVPN frees its lame duck there), and the newest becomes the one before it, with its end set to the start plus the transition window (`TransitionWindow`, 3600 seconds, OpenVPN's `--tran-window`). A key with `RenegotiateAfter` set also ends `RenegotiateAfter` plus the window after it was made.
  - **Using the keys.** The data keys of the new key state open packets as soon as the key exchange is done. Sealing moves to them after `min(HandshakeTimeout, RenegotiateAfter / 2)` (`HandshakeTimeout` when `RenegotiateAfter` is not set); until then the older key seals, or the newest if there is no other. `Write` reads the table of keys with one atomic load; the loop makes a new table, never changing one that is published.
  - **When.** `RenegotiateAfter` (a negative `Config` value means never, the client then only answers) after the newest key was made, or when its data channel says so: the 32-bit packet id at `0xFF000000`, the AEAD usage limit of the non-epoch format at 7/8 for either direction, the send epoch at `0xF000`. A failed attempt ends the session: one that takes more than `HandshakeTimeout` with `TagRenegotiationFailed` (metadata `key_id`, `timeout`), one whose TLS session, key exchange or credentials fail with that error. (Until the audit after 1.0 the attempt was thrown away and tried again with the next key id after 5 seconds, §20 V11; a real server cannot take that retry.)
  - **Ending.** When a key reaches its end and nothing newer is complete, the session ends with `TagRenegotiationFailed`; a key before the newest that reaches its end is dropped quietly. The data channel never keeps a key that is past its end.
  - **Credentials.** The first key exchange calls `Credentials`; the others do not. When the server pushed `auth-token` the password is the token and the user name is the pushed `auth-token-user` (base64) when there is one; a later `PUSH_REPLY` with `auth-token` (which a server with `--auth-gen-token` sends after each renegotiation) replaces the token for the next one. Without a token the first user name and password are sent again, as OpenVPN does; a client that wants them forgotten must use a token.
  - **Control messages and `EXIT`.** Every key state reads its control messages; `EXIT` is written to the TLS session of the newest complete key, after a renegotiation that is under way (§11.2). Only the first key state sends `PUSH_REQUEST` and has the options of the push; a later `PUSH_REPLY` changes nothing but the token.

## 12. Profiles (package `ovpn`; source `options.c`, `options_parse.c`, `doc/man-sections/`)

- **Grammar:** OpenVPN's: one option per line, `#` and `;` comments, single and double quotes, backslash escapes, a leading `--` allowed, and inline files (`<ca>...</ca>`, `<cert>`, `<key>`, `<tls-auth>`, `<tls-crypt>`, `<tls-crypt-v2>`, `<auth-user-pass>`, `<connection>`).
- **Decided in step 3.1** (`ovpn/lex.go`; source `options_parse.c` `parse_line`, `read_config_file`, `check_inline_file`, `read_inline_file`; OpenVPN's `test_parse_line`):
  - A line is split into words by white space (the C locale's: space, tab, line feed, vertical tab, form feed, carriage return). A word is bare, in double quotes or in single quotes. A backslash outside single quotes escapes only a backslash, a double quote or a white space character; anything else after it, or the end of the line, is an error (OpenVPN rejects the first too and has no line continuation). Single quotes have no escapes. A quote inside a bare word is a character; a word that ends at its closing quote and is followed at once by more text makes that text a new word. `#` and `;` start a comment at the place where a word could start and are plain characters inside a word. A quoted empty word is a word.
  - The first word is the option's name, with one leading `--` taken off. A line with one word that is `<name>` opens an inline block, which ends at the first later line that begins (after white space) with `</name>`, followed by anything; the text between is the block's text, each line with a line feed and without a carriage return, with nothing taken out (comments, indentation). A block with no end, or an empty or odd tag, is an error at the line of the opening tag. `<connection>` is such a block; step 3.2 reads its text again as options. A UTF-8 byte order mark at the start is skipped, CR LF ends a line, and a NUL byte is an error.
  - Limits: 16 words on a line (the name and 15 words), 4096 bytes in a line and in a word, 1 MiB in a profile (§20 V12). Errors: `ovpn.TagSyntax` (metadata `line`, the line where the problem is; the lines inside a block are counted), `ovpn.TagProfileTooLarge`, `ovpn.TagReadFailed`.
- **Files:** `Parse` accepts only inline files; `ParseFS` reads file options from the `fs.FS` it is given, and never from anywhere else. The parser never runs a command and never reads the environment.
- **Every option is in one of three tables**, each with a test:
  - **Supported:** what §6 to §11 implement (`client`, `remote`, `proto`, `port`, `remote-random`, `connect-timeout` (and its old name `server-poll-timeout`), `ca`, `cert`, `key`, `tls-auth`, `key-direction`, `tls-crypt`, `tls-crypt-v2`, `auth-user-pass`, `auth`, `data-ciphers`, `cipher` as a fallback offer, `remote-cert-tls`, `verify-x509-name`, `peer-fingerprint`, `tls-version-min`, `tls-groups`, `reneg-sec`, `hand-window`, `tls-timeout`, `ping`, `ping-restart`, `ping-exit`, `keepalive`, `tun-mtu`, `explicit-exit-notify`, `setenv UV_*`, `push-peer-info`, `pull-filter`, `route-nopull`, `auth-nocache`).
  - **Accepted and ignored:** options that mean nothing to a library (`dev tun`, `nobind`, `persist-tun`, `persist-key`, `verb`, `mute`, `resolv-retry`, `user`, `group`, `daemon`, `log`, `script-security`, `sndbuf`, `rcvbuf`, ...). `Profile` lists the ones that were ignored.
  - **Refused, with the option and the line in the error:** options that 1.0 cannot honor and that would be unsafe or wrong to skip (`secret`, `dev tap`, `fragment`, `compress`/`comp-lzo` with compression on, `http-proxy`, `socks-proxy`, `pkcs12`, `up`/`down` and the other scripts, `plugin`, `management`).
- **Decided in step 3.2** (`ovpn/profile.go`, `ovpn/options.go`; source `options.c` `add_option` and the pages of `doc/man-sections/`). The three tables are data in `options.go` (`handlers`, `ignoredOptions`, `refusedOptions`), each option in one of them, tested. Beyond the names that this section lists:
  - **Supported with a note:** `client`, `tls-client`, `pull` and `push-peer-info` (a client always does them), `dev` and `dev-type` (`tun` is noted in `Ignored`, `tap` is refused), `rport` (same as `port`), `ncp-ciphers` (the old name of `data-ciphers`), `explicit-exit-notify [n]` (the library always says goodbye, once: `n` beyond 1 is noted in `Ignored`), `ping-exit` (it ends the session like `ping-restart`; what comes next is the program's; a profile with both is an error), `keepalive i t` (`ping i` and `ping-restart t`), `reneg-sec 0` (never renegotiate by time), `auth-nocache` (`Config.AuthNoCache`), `setenv UV_x value` (peer info) and `setenv opt option ...` (applied if the option is in a table, else left out and noted), any other `setenv` (noted), `ignore-unknown-option names` (whole profile, wherever it is).
  - **Remotes.** `remote host [port [proto]]`; the port and the protocol come from the line, else from the `<connection>` block it is in, else from `port`/`rport` and `proto` of the profile (which may come after it), else 1194 and `udp`. `proto` is `udp`, `udp4`, `udp6`, `tcp`, `tcp4`, `tcp6`, or `tcp-client`, `tcp4-client`, `tcp6-client` (the same as without `-client`); the server forms are refused. A `<connection>` block has `remote`, `proto` and `port`/`rport` and the ignored options; any other option in it is refused, and a block with no remote is an error. A profile with no remote is read (the `Config` is still good for `openvpn.Dial`); `Profile.Dial` then fails.
  - **Files.** `ca` (several allowed, each adds to the pool), `cert` (a chain is allowed), `key`, `tls-auth [0|1]` (the digest is `auth`, SHA-1 by default, or SHA-256, 384 or 512; the direction is the argument or `key-direction`), `tls-crypt`, `tls-crypt-v2` (one protection only), `auth-user-pass`, `peer-fingerprint`: inline or a file name. A file name is read only through the `fs.FS` of `ParseFS`, relative to the directory of the profile; an absolute name, a name with a backslash, or one that climbs out with `..` is refused (`TagFileUnavailable`), and so is any file name with `Parse`. A key that is encrypted (`ENCRYPTED` in its PEM) is refused: there is no prompt and no `askpass`; a `cert` and a `key` that are not a pair, a `ca` with no certificate and a key file that is not one are `TagBadFile`. A profile with no `ca` and no `peer-fingerprint` cannot verify the server and is refused (`TagMissingOption`); a `cert` needs a `key` and the other way round. The credentials of `auth-user-pass` are the first line (the user name) and the second (the password), without their line ends; a password is never in an error.
  - **Ciphers.** `data-ciphers` keeps the AEAD ciphers that the library has (AES-128/192/256-GCM, CHACHA20-POLY1305, any case) in order and notes the others in `Ignored` as `data-ciphers: NAME`; none left is an error. `cipher X` is the last offer when X is one of the four; it alone, with an AEAD cipher, adds X to the defaults; with a cipher that is not AEAD and no `data-ciphers` it is left out (noted in `Ignored`) and the default ciphers are offered, as OpenVPN does (`options.c options_postprocess_cipher`: "OpenVPN ignores --cipher for cipher negotiations"); most profiles of providers still have `cipher AES-256-CBC`, and a server that has only that cipher fails the negotiation with its own error. In `data-ciphers`, `DEFAULT` stands for the default list and a `?` before a name (an optional cipher) is dropped (`ssl_ncp.c mutate_ncp_cipher_list`). `data-ciphers-fallback` is ignored (it is for a server that does not negotiate).
  - **TLS.** `remote-cert-tls server` (`client` is refused), `verify-x509-name name [subject|name|name-prefix]` (default `subject`), `peer-fingerprint` (SHA-256, with or without colons, arguments or an inline block with one or more per line), `tls-version-min 1.2|1.3 [or-highest]` (1.0 and 1.1 are accepted and noted in `Ignored`: it is a lowest version, and the library starts at 1.2), `tls-groups` (colon list of `secp256r1`/`prime256v1`/`P-256`, `secp384r1`/`P-384`, `secp521r1`/`P-521`, `X25519`, `X25519MLKEM768`, `SecP256r1MLKEM768`, `SecP384r1MLKEM1024`; any other name is refused, so a list is never half taken).
  - **Ignored in addition to the names above** (they mean nothing to a library or only widen what it does): `local`, `lport`, `float`, `connect-retry`, `connect-retry-max`, `key-method`, `tls-cipher`, `tls-ciphersuites`, `tls-version-max`, `reneg-bytes`, `reneg-pkts`, `replay-window`, `auth-retry`, `redirect-gateway`, `route`, `route-ipv6`, `dhcp-option`, `block-outside-dns`, `topology`, `ifconfig`, `link-mtu`, `tun-mtu-extra`, `ecdh-curve`, `dh`, and the others of `ignoredOptions`. The routes and DNS options of the profile itself are local settings of a program that has a TUN device; the library makes none.
  - **Refused in addition:** `mode`, `tls-server`, the options of proxies (`http-proxy-*`, `socks-proxy-retry`), `askpass`, `cryptoapicert`, `capath`, `extra-certs`, `crl-verify`, `verify-hash` (use `peer-fingerprint`), `remote-cert-ku`, `remote-cert-eku`, `ns-cert-type`, `x509-username-field`, `ncp-disable`, `tls-verify`, `management-*`, `route-up`, `route-pre-down`, `up-restart`, `down-pre`, `auth-gen-token-secret`, `tls-export-cert`, with the reason in the error: each of these limits what the server may be or how it is verified, or runs something, so skipping it would not be what the profile says.
  - **Errors** (`TagUnsupportedOption`, `TagBadOption` with `option`, `line` and `reason`; `TagMissingOption`, `TagFileUnavailable`, `TagBadFile`; the grammar's tags of step 3.1; and the `InvalidConfig` error of `Config.Validate`, because a profile whose values the library refuses (a `tun-mtu` out of range) is refused when it is read): none has the value of an argument, a key or a password.
- An option that is in no table is refused, unless the profile has `ignore-unknown-option` for it or it is under `setenv opt`.
- A password is never read from a terminal: `auth-user-pass` with no file makes a `Config` with no credentials and `Profile` says that the profile asks for them.
- **`mssfix`** (after 1.0, §21 O34; `ovpn/options.go hMSSFix`): `mssfix` sets the default, `mssfix N` sets `Config.MSSFix` (a number 0 to 65535; 0 turns the clamp off, as in OpenVPN, and is stored as -1; a size below 154 fails as the invalid config of the field `MSSFix`), and a second word `mtu` or `fixed` sets `Config.MSSFixMode`; any other word, or more words, is `TagBadOption`. In a `<connection>` block it is ignored and listed (§20 V14).
- **Decided in step 3.3** (`ovpn/dial.go`; source `doc/man-sections/client-options.rst`: `--remote`, `--remote-random`, `--connect-timeout`, `--server-poll-timeout`): `Profile.Dial(ctx)` tries the remotes once each, in the order of the profile, or in a random order made by `crypto/rand` at each call with `remote-random`. Each remote gets `ConnectTimeout` (120 s when the profile has none) **to answer**: for the link to be made and the first packet of the server to come; it is `Config.ServerPollTimeout` of the attempt, which has a copy of the profile's `Config` (changed after 1.0, §21 O32: it used to bound the link and the whole handshake, from the manual page, while OpenVPN's `check_server_poll_timeout` restarts only `if (!tls_initial_packet_received(...))`; a profile with `server-poll-timeout 4` then cut every login that took longer). A server that has answered has `HandshakeTimeout` for the handshake. The next remote is tried when one fails, whatever the cause. When ctx is done it stops at once, without trying another remote. When all failed, the error of the last remote is returned, with `remotes_tried` and `remotes` added to its metadata (a route does not change). `server-poll-timeout` is the old name of `connect-timeout` and is read as it (it is no longer in the ignored table). A profile with `auth-user-pass` and no file needs `Config.Credentials`; without it `Dial` fails with `TagCredentialsMissing` before it tries a remote, and a profile with no remote (one that was made by hand) with `TagNoRemotes`. **Deviation from OpenVPN (§20 V13):** OpenVPN goes round the list again and again (`--connect-retry`, `--connect-retry-max`) and waits between the rounds; `Dial` makes one round and returns, as a library does: the program decides whether and when to try again (a client that reconnects by itself is after 1.0, §22).

## 13. Userspace network (package `vpnnet`)

- **D4.** The TCP/IP stack is gVisor's `tcpip` with its `gonet` adapters (Apache-2.0, through the linking exception of `NOTICE`; the owner's decision, 2026-11-21). It is imported only here: a program that uses only `openvpn` does not compile it.
- `New` makes a stack with one interface whose link is the `*openvpn.Conn`, with the addresses, the MTU and the DNS servers of `ConnectionState`. Everything dialed through the `Net` goes into the tunnel; the pushed routes are not needed to decide that.
- TCP and UDP over IPv4 and IPv6, and ICMP echo. `network` and `address` mean what they mean in `net`.
- `Resolver` returns a `*net.Resolver` whose queries go through the tunnel to the DNS servers of the VPN; `DialContext` uses it for host names.
- `Close` closes the stack and its connections. It does not close the `*openvpn.Conn` unless `Options` says so. When the tunnel ends, the connections of the `Net` fail with the errors of §5.3.
- **Decided in step 3.4** (`vpnnet/`; gVisor `go` branch, version in §19):
  - One NIC with no link layer: a `channel.Endpoint` with the MTU of `ConnectionState`, the addresses of `ConnectionState().Addrs` (each with its prefix length), and a default route for IPv4 and for IPv6 into it. The packets that the stack sends are written to the `Conn`; the packets that the `Conn` reads are given to the stack (IPv4 or IPv6 by the first nibble; anything else is dropped). Two goroutines do this; both stop at `Close`, and when `Close` returns no goroutine of the `Net` (nor of gVisor's stack) runs.
  - `New` needs a `Conn` whose handshake is complete (`TagNotConnected`); a stack that cannot be set up is destroyed before `New` returns (`TagStackSetupFailed`). A `Net` takes over the `Read` of its `Conn`: to end that `Read` without closing the `Conn`, `Close` sets a read deadline in the past and clears it again when the goroutine has returned.
  - When the `Conn` fails, the `Net` is down: its connections and listeners fail (with gonet's errors, as §5.3 says), and `DialContext`, `Listen` and `ListenPacket` return the error that ended the `Conn` (`io.EOF` when the server left); after `Close` they return `net.ErrClosed`.
  - Addresses are IP literals until step 3.5 (`TagBadAddress` for a host name, a zone, a missing port, a family that the network does not name); `Listen` and `ListenPacket` also take an empty host: every address, IPv4 and IPv6 for `tcp` and `udp`, one family for `tcp4`, `tcp6`, `udp4` and `udp6` (IPv6 only, as `net` does). A port of 0 takes a free port. Errors: `TagUnsupportedNetwork`, `TagBadAddress`, `TagDialFailed` (the cause is behind it: `context.Canceled`, `context.DeadlineExceeded`, a refused connection), `TagListenFailed`; the tag strings begin with `Net` so that they differ from the ones of package `openvpn`.
- **Decided in step 3.5** (`vpnnet/dns.go`, `vpnnet/dial.go`):
  - `Resolver()` is `&net.Resolver{PreferGo: true, Dial: ...}` made once by `New`. Its Dial function ignores the address that the resolver asks for and connects through the tunnel to port 53 of the pushed DNS servers (`ConnectionState().DNSServers`, those of a family that the tunnel has), in order, starting with the one that worked last; a connection that is refused goes on to the next server, and a server whose read fails (an error, or a deadline) gives its place to the next one at the next attempt of the resolver. The connection of a UDP query is a `net.PacketConn` (the resolver tells datagrams from streams by the type). With no DNS server pushed the lookup fails with a `*net.DNSError` that says so (`TagNoDNSServers` is what the Dial function returns; the standard library keeps only its text). **Known limit of `Resolver()`:** Go's resolver still reads the host's `/etc/hosts` and `/etc/resolv.conf` (the search list, `ndots`, the number of attempts and the timeout) where they exist, so a name can be answered from the host's files and not from the VPN. For that reason `Net` has its own DNS client (the next point), which `DialContext` uses. gVisor sends no ICMP error for a UDP datagram to a closed port, so a DNS server that is down shows as the resolver's timeout (5 s by default), not as a refusal.
  - `DialContext` with a host name looks it up with `LookupNetIP` (`ip4` when the network is `tcp4` or `udp4` or when the tunnel has only IPv4, `ip6` likewise, `ip` when both), skips the addresses of a family that the tunnel does not have, and tries the others in the order of the answer until one connects (the context bounds all of it). A name that cannot be looked up returns the error of `LookupNetIP`, untouched (`TagNoSuchHost`, `TagNoDNSServers`, `TagDNSQueryFailed`, ...); a name whose addresses are all of a family that the tunnel lacks is `TagResolveFailed`. `Listen` and `ListenPacket` still take IP literals only. Names are checked to have only letters, digits, hyphens, underscores and dots (at most 253 bytes); anything else is `TagBadAddress`.
  - **Own DNS servers and a DNS client that reads nothing of the host** (the owner's request, 2026-11-22). `Options.DNSServers []netip.AddrPort` replaces the pushed servers (port 0 is 53; a server of a family that the tunnel lacks is skipped); with none, the pushed ones are used. `Net.LookupNetIP(ctx, "ip"|"ip4"|"ip6", host)` and `Net.LookupHost` are a DNS client written for this package (no new dependency; `golang.org/x/net/dns/dnsmessage` was not added): it sends an A and an AAAA query over UDP through the tunnel (2 s per try, 2 tries per server), asks again over TCP when the answer is truncated, goes on to the next server when one fails (a SERVFAIL, a timeout, a bad answer), and takes "no such name" (NXDOMAIN) as an answer of the server (no other server is asked). **Changed by the audit after 1.0:** a server that failed is tried after the others for 30 seconds (`dnsCooldown`) and then has its place again (before, the lookups stayed with the next server for the life of the `Net`, so one lost answer of an internal server that is pushed first made the internal names unknown); both types are always asked, and the addresses of one type are the answer when the server says "no such name" for the other (RFC 4074 §4.2; before, that threw the addresses away); an error answer with no question section (REFUSED, SERVFAIL) is taken as the error at once, by its id (before, it was waited out for 4 seconds). A context that ends wakes the query at once (`context.AfterFunc` moves the deadline of the connection to the past). After `Close` the lookups return `net.ErrClosed`, as `DialContext` does. It never reads `/etc/hosts` or `/etc/resolv.conf`; the name is asked as given, with no search list and no `ndots`, and an IP literal is returned as it is. Answers are accepted only with the id and the question that were sent; records that are not A/AAAA of the name's type (a CNAME) are skipped, the servers being recursive. The A and the AAAA queries are made one after the other. Tags: `TagNoSuchHost`, `TagBadHostName`, `TagUnsupportedLookup`, `TagDNSQueryFailed`, `TagDNSServerError`, `TagBadDNSResponse` (and `TagNoDNSServers`). `DialContext` returns the error of the lookup untouched; `TagResolveFailed` is now only "the name has addresses but none that the tunnel can reach". `Resolver()` uses the same servers but is still Go's resolver. `FuzzParseResponse` covers the parser of answers.
  - Throughput (`BenchmarkThroughput`, 100 MiB through `vpnnet` and the real server, in `IMPLEMENTED.md`) is the number to watch, not a requirement.
  - **Known limit (found by the soak test of step 4.2):** with heavy loss on the tunnel (the soak profile, `loss 10% delay 20ms reorder 25% duplicate 5%` on a UDP tunnel, which is about 19% lost on a round trip) and a TCP connection whose two directions are both saturated (an echo of 10 MiB), the connection stands still for minutes and then times out. The packet capture shows why: the Linux end, whose receive queue is full, shrinks its window below what gVisor has already sent; gVisor's later pure acknowledgements carry a sequence number beyond that window, Linux drops them as out of window (and their acknowledgement with them) and answers with a duplicate ack, and gVisor does not send the segment that would end it before its retransmission timer, which in this state ran for minutes (its maximum is 120 seconds). The library's own layers are not at fault (the data channel answers 77% of the pings under the same faults, and kernel TCP over the same faults does the echo in 12 seconds). The same transfer passes with 5% loss, with the two directions one after the other under the full profile (`TestSoakNetem`), and with a TCP tunnel. **Not fixed:** lowering gVisor's maximum retransmission timeout (`tcpip.TCPMaxRTOOption`) was tried and did not remove the stall (it also makes gVisor give up a connection after that long without progress, since gVisor takes the maximum as its time limit), so it was not kept. A program that expects such a link should put a deadline on its connections.
  - The tests of the package run on real time and not on `testing/synctest`: gVisor's goroutines wait in a way that the bubble does not count as blocked, so its clock does not advance and a test that needs a timer would wait for ever. They wait for events, and the only timed case is a context that expires after 100 ms.

## 14. Errors

### 14.1 Rules
All errors use `github.com/rm4n0s/errors` v0.3.1 the way its `AI_GUIDE.md` says (the owner's requirement). `internal/tools/errcheck` checks rules 1 to 8.

1. No `fmt.Errorf`. The standard `errors` package is never imported under the name `errors`: the error package re-exports `Is`, `As`, `Unwrap` and `Join` (an alias `stdErrors` when something else of the standard package is needed).
2. `errors.New` has a tag and a message; metadata goes in the same call as key/value pairs.
3. An error from outside the module is tagged once, with `NewErr`, where it first appears. An error from a function of the module is returned untouched.
4. A constructor is called in the function that fails, never in a helper that builds the error.
5. A tag is a constant declared next to the code that produces it; exported (`TagX`, documented) when a user of the library may branch on it. Code branches on tags or `errors.Is`, never on messages.
6. A sentinel is a struct literal `&errors.Error{Tag: TagX}`, never a package-level `errors.New`.
7. Functions return `error`, never `*errors.Error`.
8. Every tag has a route test: a test checks with `HasRoute` a route that ends with the tag. `internal/tools/errcheck` accepts any string of a test file that ends with `.Tag`, written out or made of constants, so that a table of routes is a route test.
9. **No secret in an error:** no key, password, token, or decrypted payload in a message or in metadata. Metadata values are JSON-serializable.
10. Errors are logged with `slog` as the attribute `"err"`.
11. The exception of §5.3 is the only place where an untagged error leaves the module.
12. **Work whose error leaves its goroutine is handed off with `errors.Async`**, called in the function that starts the goroutine and not inside it, so that the route of the error begins at that function and not at the top of the goroutine. The work returns its error, and the error is stored, sent or given to another goroutine only after it has passed through the hand-off, which gives it its route: an error that is stored before has the short route until then. An error that another goroutine can already read is never changed by hand (`SetMetadata`, `RemoveMetadata`, `SetMessage`). Like rules 3 and 4 it is not checkable by the tool: the reviewer checks it, and the route tests of §14.2 hold it for the goroutines of a session.
13. `errors.AsyncRecover` is not used: nothing in the module turns a panic into an error, and doing so is a decision of the owner. `errors.Join` and `errors.All` are for the errors of several goroutines that are all wanted; a connection ends with one error (§14.2), so the module joins none. `errors.All` also reads the errors inside a wrapped one: the cause of `TagTLSHandshakeFailed` when it is an error of this module (a check of the server's certificate).

### 14.2 The error that ends a connection
It is made once, in the goroutine that found the failure, and stored. Every later `Read`, `Write` and `HandshakeContext` returns that same value, so its route shows where the session failed, not who asked.

**The route begins at the call that started the session** (with errors v0.3.1, 2026-11-26). The goroutines of a session are started by the first `HandshakeContext` (which `Dial` calls, and a first `Read` or `Write` too), and `Session.start` hands their work off with `errors.Async` (§14.1 rule 12). `TagServerPollTimeout` out of `Dial` has the route `Dialer.Dial->Conn.HandshakeContext->Session.Handshake->Session.start->Session.loop.ServerPollTimeout`; before, it was `Session.loop.ServerPollTimeout`. No frame of the Go runtime is in a route any more.
- **The goroutines and their routes**, after `...->Session.Handshake->Session.start->`: the loop (`Session.loop->...`), the reader of the link (`Session.readLoop`), its writer (`Session.writeLoop->Session.writeLink`), the TLS goroutine of the first key (`Session.startTLS->Session.startTLS.func1->Session.tlsMain->...`, with `Session.controlLoop->Session.control` for a control message of the server), the sender of `PUSH_REQUEST` (`Session.pushRequests`), and the close of the link, whose error `Close` returns (`Session.closeLink`).
- **The TLS goroutine of a renegotiation** is started by the loop, so its route goes on through the loop: `Session.loop->Session.renegTick->Session.beginKey->Session.startTLS->...` for the client's renegotiation, `Session.loop->Session.handle->Session.acceptSoftReset->Session.beginKey->Session.startTLS->...` for the server's. Work that was handed off and hands more work off gives a route with both parents only when the error returns through both hand-offs (when it does not return through the outer one, the route starts at the function that the outer goroutine ran), so every error of that goroutine goes to the loop, which returns it: the failure of the renegotiation as before, and now also what ends the session after the key was made (the server's `HALT`, `RESTART`, `EXIT` or `AUTH_FAILED` in the TLS session of the new key, a TLS session that broke). `io.EOF` for the server's `EXIT` goes the same way and stays `io.EOF` (§5.3). For the same reason the hand-off of the sender of `PUSH_REQUEST` is made in `Session.start`, and its route does not name the TLS goroutine that starts it.
- **The order.** The function of a goroutine returns the error, and its goroutine stores it when it has passed through the hand-off; until then no other goroutine can read it. What a goroutine did after it had stored its error it now does after its function has returned: the loop closes the link, the writer of the link sends what is left after `Close`. In the short time between the failure and the storing, another goroutine or a `Write` of the caller can find the same failure and store its own error first; either is the error of that failure.
- **Errors that the caller's goroutine makes** have the caller's route, as before: a `Write` whose own write of the link fails (`Conn.Write->Session.Write->Session.writeLocked->Session.writeLink.LinkFailed`), the end of the packet ids, and a `HandshakeContext` whose context is done.
- **`vpnnet`** hands the error that ended the `Conn` on (`Net.fail`), and its calls return it. `New` hands the work of its two goroutines off. The error that the `Conn` has stored was made in a goroutine of the session and keeps its route. The writer of the Net can make that error itself, with its `Write` of the `Conn` (a write of the link that fails): its route begins at `New`, `New->Net.writeTunnel->Conn.Write->Session.Write->Session.writeLocked->Session.writeLink.LinkFailed`. The session stores that error a moment before it comes back through the hand-off of the Net, so a reader in between sees the route without `New` in front.
- **Callers that use the same error package.** The stored error is shared by every goroutine that uses the `Conn`, so it must not be changed by hand (`SetMetadata`). A caller's own `errors.Async` is safe (errors v0.3.1: the stack of an error is replaced as a whole, under a lock). When a session was started below the caller's hand-off and its error returns through that hand-off, the route of the stored error gains the caller's part, for every holder of the error; until then it begins at the function that the caller's goroutine ran.
- **Logs.** An error that a goroutine of a session logs itself, before it returns it (a dropped packet at the debug level, `a renegotiation failed`), has not passed through the hand-off: its logged route begins at the function of the goroutine (`Session.loop->Session.handle->...`), as it did before.

### 14.3 Exported tags
The list grows with the steps. The ones a caller will branch on: `TagHandshakeTimeout`, `TagServerPollTimeout` (no packet of the server within `Config.ServerPollTimeout`, the `connect-timeout` of a profile; metadata `timeout`), `TagServerCertificateUsage` (`remote-cert-tls server` and a certificate without the usages; metadata `missing`), `TagTLSHandshakeFailed`, `TagAuthFailed` (metadata: `reason`, `session`, `temporary`, `backoff` in seconds, `advance`), `TagServerHalt` (metadata: `reason`), `TagServerRestart` (metadata: `reason`, `flags`), `TagPingTimeout`, `TagCipherNegotiationFailed`, `TagKeyDerivationUnsupported`, `TagUnsupportedPushedOption` (metadata: `option`), `TagLinkFailed`, `TagKeyExchangeFailed` (metadata: `op`), `TagKeyExchangeTooLong` (credentials that do not fit in the message that a server reads; metadata: `length`, `max`), `TagCredentialsFailed`, `TagDialFailed` (metadata: `network`, `address`), `TagUnsupportedNetwork` (metadata: `network`); in `ovpn`: `TagUnsupportedOption` (metadata: `option`, `line`), `TagBadOption`, `TagMissingOption`, `TagFileUnavailable`, `TagSyntax`, `TagNoRemotes`, `TagCredentialsMissing`; in `vpnnet` (the tag strings begin with `Net`): `TagNotConnected`, `TagUnsupportedNetwork`, `TagBadAddress`, `TagDialFailed`, `TagResolveFailed`, `TagListenFailed`, `TagNoDNSServers`, `TagNoSuchHost`, `TagBadHostName`, `TagUnsupportedLookup`, `TagDNSQueryFailed`, `TagDNSServerError`, `TagBadDNSResponse`. ## 15. Security rules

1. Random bytes come from `crypto/rand`.
2. MACs and tags are compared in constant time (`hmac.Equal`, the AEAD's `Open`).
3. A packet is authenticated before anything in it is used, and its replay id is accepted only after it authenticated.
4. A nonce is never used twice with a key (§10).
5. Bytes from the network or from a file are parsed with explicit bounds; every length is checked before it is used; every parser has a fuzz target. No `unsafe` in this module's own code (gVisor, which `vpnnet` links, has its own).
6. Buffers that the peer can make grow have a limit (control message reassembly, the reorder window, the pushed options).
7. A packet that anyone could have sent (unauthenticated, replayed, malformed) never ends the session and never costs more than its own processing.
8. No secret in logs or errors (§14.1 rule 9). The logger gets the names and sizes of things, never their bytes.
9. The server's certificate is verified by default. Turning that off takes an explicit setting of the caller's `tls.Config`; the profile parser never does it by itself.
10. Key material is dropped when its key slot ends and when the connection closes.
11. The parser of profiles reads only what it is given (§12).

## 16. Concurrency and lifetime

- A connection owns its goroutines: the reader of the link, the loop (which owns the state and the timers of the control channel), the writer of the link and the TLS session of each key. They start at the handshake and none runs after `Close` returns; a test checks it. Their work is handed off with `errors.Async`, and each returns the error that ends the session to its own goroutine, which stores it (§14.2).
- No global mutable state. Two connections share nothing but an unchanged `Config`.
- Time is the standard `time` package; the tests run it with `testing/synctest`, so no test sleeps. The exceptions are the tests of `vpnnet` (gVisor's goroutines do not work with the bubble's clock, §13; they wait for events) and the tests against the real server, which run on real time.
- The data path does not allocate per packet in the steady state (a benchmark with `ReportAllocs` holds it).

## 17. Testing

- **Unit tests** need nothing but Go: the peer is `internal/vpntest` in the same process, over `net.Pipe` or an in-memory link with loss, reordering and duplication. They run on every platform, with and without cgo, under the race detector.
- **Tests against the real server** carry the `gopenvpn_server` build tag and run under `scripts/vpn-ns.sh`, which enters a private user and network namespace (`unshare -Urn`), so they need no root and change nothing on the machine. `internal/servertest` makes the certificates and keys in Go, starts `openvpn` 2.7.9 on the loopback of the namespace with the options of the test, reads its log, and stops it (and starts the real `openvpn` client, for the check that it reads the same profile, and Wine, for the programs built for Windows). They skip when `openvpn` or the namespace is missing. The server runs with `--disable-dco`: inside the namespace the kernel data channel cannot create its peer (§21 O17); `Options.EnableDCO` is there for a machine where it can, and no test uses it.
- **A behavior of the protocol counts as implemented when a test against the real server shows it.**
- **Known answers:** what OpenVPN's own unit tests check with fixed vectors (`tests/unit_tests/openvpn/`) is checked with the same vectors.
- **Faults and long runs:** `tc netem` on the loopback of the namespace gives loss, delay, reordering and duplication to the soak tests (build tag `gopenvpn_soak`, run by hand, listed in `CLAUDE.md`), which also hold the one-hour renegotiation run and the 1000-connection leak test.
- **Fuzzing:** a target for every parser (19 in 1.0), with its seeds in the code (`f.Add`); a finding goes to `testdata/fuzz/` of its package as a regression test. All of them ran for 10 minutes without a finding at step 4.2.
- **Errors:** every tag has a route test (§14.1 rule 8). The route of an error that a goroutine of a session makes is asserted across the hand-off, from the `Handshake` that started the session down to the tag (`internal/session/route_test.go` has a case for each goroutine).
- **Leaks:** a test opens and closes connections many times and checks the goroutines and the heap.
- No test connects to a server on the internet.

## 20. Decisions and deviations

**Decisions**
- **D1** GPL-2.0-only, with the Apache2 linking exception (§2).
- **D2** The three standard error values are returned untagged (§5.3).
- **D3** 1.0 needs keys from the TLS exporter (§8.3).
- **D4** gVisor is the userspace stack, in `vpnnet` only (§13).
- **D5** One `Conn` is one session; reconnecting is the caller's, until a later version (§4.1).
- **D6** OpenVPN's code is the reference for the protocol, not a design to translate (§2).

**Deviations from OpenVPN** (each also has a `// Deviation:` comment in the code)
- **V1** No options string check: the client sends OpenVPN's options string for compatibility and does not compare the server's (OpenVPN 2.7 removed `--opt-verify`).
- **V2** No scripts, plugins, management interface or environment: a library gives its caller values and errors instead.
- **V3** The profile parser refuses what it cannot honor instead of warning and going on (§12).
- **V4** `internal/wire` parses strictly: an `ACK_V1` with bytes after its acknowledgements is refused (OpenVPN ignores them; no real server sends them), and the opcodes 1, 2 and 12 to 31 are refused (OpenVPN 2.7.9 accepts 3 to 11 only).
- **V5** `internal/keys` refuses a static key file of 128 bytes (one key), which OpenVPN reads for `tls-auth` with no direction. `openvpn --genkey` writes 256 bytes, and a profile with an older key can be given a new one.
- **V6** `internal/reliable` counts, for the fast retransmission, only the first acknowledgement of each later packet. OpenVPN counts every acknowledgement of a later id against the earlier packets, so an id that the peer repeats in each packet (as OpenVPN itself does, §7.2) can bring on a retransmission that no loss asked for. The wire does not change, and the draft's rule ("three packets sent later were acknowledged") is kept as written.
- **V7** `ConnectionState.PushedOptions` and the `Pushed` record keep the word `auth-token` and not its value, where OpenVPN keeps the option as received: a caller that logs the state must not log the token (§15 rule 8). The token itself is kept in memory for the reconnect that §22 has for later.
- **V8** Control messages are cut at the NUL, not at the TLS record (§9). OpenVPN reads one message for each record, so a record that holds half a message breaks it; here it does not. The server sees no difference.
- **V9** A pushed `compress` or `comp-lzo` is refused whatever its argument, `stub` and `no` included: they all add a byte of framing to every data packet, which the data channel of 1.0 does not parse (§22).
- **V10** No limit on failed verifications: OpenVPN stops decrypting with a key after more than 2^36 failed authentications (`cipher_decrypt_verify_fail_exceeded`, the bound of DTLS 1.3). Here a forged packet is counted and dropped and never turns a key off, so that whoever can send packets to the client cannot end its session (§15 rule 7); a key lives for an hour, and 2^36 forgeries in that time (about 19 million a second) are beyond what a link carries.

- **V11** A renegotiation that fails ends the session (`TagRenegotiationFailed`, or the error that made it fail); the caller dials again. OpenVPN's client throws the TLS session away and starts a new one (a new session id, hard resets) inside the same process, with the old key still carrying data; this library has one session for a `Conn`, and reconnecting is the program's (§22). **Changed after 1.0 (the owner's decision, 2026-11-22):** until then the failed attempt was dropped and tried again with the next key id, on the reasoning that this "keeps the peer's state". It does not: a real server whose renegotiation failed moves its session aside and drops every later soft reset of it (`ssl.c tls_multi_process` `move_session(multi, TM_LAME_DUCK, TM_ACTIVE, ...)`, then `tls_pre_decrypt` "received control packet with stale session-id"), and one that never saw the attempt drops the retry because the key ids are out of step ("local/remote key IDs out of sync"). The retry could only work against the test server of this repository, and the session died an hour later, when the old key did.

- **V12** The grammar of profiles is OpenVPN's, with other limits and no silent cuts (`ovpn/lex.go`): a line or a word longer than 4096 bytes (OpenVPN: 256), or more than 16 words on a line, is an error (OpenVPN cuts a line that is too long into two, or drops the words after the 16th, without saying so). A backslash at the end of a line is an error (OpenVPN keeps the line feed in the word). A `#` or `;` after a backslash is an error (OpenVPN reads it as the start of a comment). An inline block's lines lose their carriage returns.
- **V13** `Profile.Dial` goes through the remotes once and returns (`ovpn/dial.go`); OpenVPN repeats the list (`--connect-retry`, `--connect-retry-max`, with a wait between the rounds) and never gives up by default. A library leaves the repetition and the wait to the program that calls it; one `Dial` is one round, and the error of the last remote says how many were tried. `remote-random` uses `crypto/rand` for the order, which OpenVPN does with its own generator.
- **V14** The MSS clamp (§10): a packet whose IPv4 header length is below 20 bytes is not touched (OpenVPN reads it as an IPv4 packet with a header of that length, which is not one); and `mssfix` in a `<connection>` block is ignored (OpenVPN uses it for that remote), because the `Config` has one `MSSFix` for every remote.

## 21. Observations

What the documentation or the draft does not say or says differently from the code, and what was found by running the real server. Each entry names the test that shows it.

Known before any code, to be confirmed by their steps:
- **O1** The draft shows the acked packet ids as 8 bytes each in one figure and 4 in another; the code uses 4 (`packet_id_type`; read in `reliable_ack_parse`, step 1.4). The real server confirms it in step 1.10.
- **O2** The draft's description of the old key derivation is incomplete; it does not matter for 1.0 (D3).
- **O3** The draft has opcodes 12 to 14; OpenVPN 2.7.9 stops at 11.
- **O4** A real OpenVPN 2.7.9 server starts with no root inside `unshare -Urn`, with a kernel DCO device, on this machine (tried 2026-11-21).
- **O5** The server refuses `--verify-client-cert none` unless an authentication method is configured (`--auth-user-pass-verify`, a plugin or the management interface): `Options error: --verify-client-cert none|optional must be used with --management-client-auth, an --auth-user-pass-verify script, or plugin`. The test server therefore requires a client certificate by default (`internal/servertest`, step 1.3).
- **O6** The server's log has the line `Initialization Sequence Completed` when it is ready, and `UDPv4 link local (bound): [AF_INET]127.0.0.1:<port>` (for TCP, `TCPv4_SERVER link local (bound): ...`) when it listens (step 1.3).
- **O7** The server answers a first reset (`CONTROL_HARD_RESET_CLIENT_V2`) **statelessly**: it sends an HMAC based reset challenge (a `CONTROL_HARD_RESET_SERVER_V2` whose session id is derived from the client's) and keeps no state. At `--verb 4` it logs nothing for that packet; at `--verb 7`: `Reset packet from client, sending HMAC based reset challenge`. `TLS: Initial packet from ...` is logged only after the client's third packet. A packet with a wrong `tls-auth` HMAC gets no answer, and at `--verb 7` the log says `Authenticate/Decrypt packet error: packet HMAC authentication failed` and `TLS Error: incoming packet authentication failed from ...` (step 1.5).
- **O8** The format of `tls-auth` in the plan is exact: first byte, session id, HMAC, packet id (4 bytes), time (4 bytes), body, with the HMAC over packet id, time, first byte, session id and body, and the keys by direction. The real server 2.7.9 accepted and answered it with `--auth` SHA1 (the default), SHA256, SHA384 and SHA512, with `key-direction` 0 on the server and 1 on the client, and with no direction on both (step 1.5, `internal/ctrlwrap/realserver_test.go`).
- **O9** The format of `tls-crypt` in the plan is exact: first byte, session id, packet id (4 bytes), time (4 bytes), tag (32 bytes), body encrypted; the tag is HMAC-SHA256 over first byte, session id, packet id, time and the plaintext (the **wire order**, unlike `tls-auth`, whose HMAC puts the packet id first); the IV is the first 16 bytes of the tag; AES-256-CTR with the first 32 bytes of the cipher key. A client sends with key 1 and receives with key 0. The real server 2.7.9 answered a `tls-crypt` reset (step 1.6, `TestTLSCryptWithRealServer`). A packet with another key gets no answer and the server logs `tls-crypt unwrap error: packet authentication failed` and `TLS Error: tls-crypt unwrapping failed from ...` (verb 7). A `tls-auth` packet sent to a `tls-crypt` server is not answered either.
- **O10** The format of `tls-crypt-v2` in the plan is exact (step 1.7). A client key made by `openvpn --genkey tls-crypt-v2-client` is read by `ParseTLSCryptV2ClientKey`; the first packet is `CONTROL_HARD_RESET_CLIENT_V3` with the wrapped key `WKc` appended after the `tls-crypt` packet, not encrypted. The server answers it statelessly (log, verb 7: `Reset packet from client, sending HMAC based reset challenge`) with a `CONTROL_HARD_RESET_SERVER_V2` whose payload is the early negotiation TLV that asks for `WKc` again, and the client's next packet, `CONTROL_WKC_V1` (ack of the reset, packet id 1, `WKc` appended again), is accepted: the log says `Valid packet (P_CONTROL_WKC_V1) with HMAC challenge from peer (...), accepting new connection.` and the server acks it with an `ACK_V1`.
- **O11** `TLS: Initial packet from` is logged only for a packet that is a hard reset, so it is not in the log of a `tls-crypt-v2` handshake, whose third packet is a `CONTROL_WKC_V1`. A third packet that is a plain `CONTROL_V1` without `WKc` starts no session; a client key made for another server gets no answer to its first packet.
- **O12** Over UDP the server accepts an `ACK_V1` as the third packet for every protection but `tls-crypt-v2`: it logs `Valid packet (P_ACK_V1) with HMAC challenge from peer (...), accepting new connection.` and reads the ack (`P_ACK_V1 kid=0`). Over TCP there is no stateless answer: the server keeps the connection and starts the session at the reset (`TLS: Initial packet from ...`), then reads our `ACK_V1`; with `tls-crypt-v2` it does not ask for the wrapped key again over TCP, so the third packet is an `ACK_V1` there too. In the log of a protected packet the `pid=[ #n ]` is the replay id of `tls-auth` or `tls-crypt` (the `tls-crypt-v2` ids start at 251658241, 0x0f000001), not an acknowledged id (step 1.10, `TestDialWithRealServer`).
- **O13** The server logs `Control Channel: TLSv1.3, cipher ...` (`session_move_active`) only when the key exchange is done, not when the TLS handshake is: the line cannot be used as a proof of step 1.11 and comes with step 2.1. What the server logs at the end of the TLS handshake is `VERIFY OK: depth=1, CN=gopenvpn-conn test CA` and `VERIFY OK: depth=0, CN=client`, the check of our certificate (`TestTLSWithRealServer`).
- **O14** A client without a certificate (TLS 1.2, so that the client sees the refusal) gets different answers by the link: over TCP the server closes the connection, and the client sees it as a failed TLS handshake or as the end of the link (`TagLinkFailed`, cause `io.EOF`), whichever of its goroutines finds it first; over UDP the server stays silent and the client's handshake times out (`TagHandshakeTimeout`). With TLS 1.3 the client's handshake completes before the server looks at the certificate; the refusal comes later and is the key exchange's to see. A client that trusts another authority fails by itself, at once, on both links.
- **O15** The ClientHello of Go's `crypto/tls` (with the hybrid post-quantum key share) is about 1.5 KB and does not fit one control packet: it goes in two, the first a `CONTROL_WKC_V1` of at most `1108 - len(WKc)` bytes for `tls-crypt-v2` over UDP, and the real server puts them back together. A client certificate of 12 KB (a dozen packets, twice the send window) also works with the real server over UDP and TCP.
- **O16** The real server accepts `IV_VER=gopenvpn-conn 0.2.0`, and logs the peer info with the space turned into an underscore (`peer info: IV_VER=gopenvpn-conn_0.2.0`, `UV_FROM=gopenvpn-conn_tests` for the value `gopenvpn-conn tests`): it makes the values safe for the environment of its scripts. With `--auth-user-pass-verify ... via-file --username-as-common-name` and a client certificate it logs `TLS: Username/Password authentication succeeded for username 'alice' [CN SET]`; with a wrong password, `TLS Auth Error: Auth Username/Password verification failed for peer`, and the handshake of the client is not ended by it: the AUTH_FAILED message comes after the server's key exchange message (step 2.3 reads it; O19). The options string of this library, which differs from what the server expects, gets no warning at `--verb 7` that matters and no refusal (`TestKeyExchangeWithRealServer`).
- **O17** A test server must run with `--disable-dco`: inside the private namespace the kernel data channel cannot create its peer (`dco_new_peer: netlink reports error (-28): Operation not permitted`), and the server then answers every client with `AUTH_FAILED` right after the key exchange. The earlier steps never saw it because their `Dial` returned before the server had decided. `servertest` disables DCO by default now (`Options.EnableDCO` turns it on, for a host that can).
- **O18** Because the client announces `IV_PROTO` bit 3 (TLS exporter), the server pushes `key-derivation tls-ekm` (D3) with its first reply, and `tun-ipv6` with `--server-ipv6`; the reply also has `route-gateway`, `topology subnet`, `ping` and `ping-restart` (from `--keepalive`), `ifconfig`, `ifconfig-ipv6 <address>/<bits> <gateway>`, `peer-id`, `cipher` and `tun-mtu`. A reply with more than about 1 KB of options comes in parts, each ending in `push-continuation 2` but the last, which ends in `push-continuation 1` (`TestPushWithRealServer`, `TestPushInPartsWithRealServer`). The server pushes `compress lz4` when asked to (`--push`), which the client refuses.
- **O19** A real server answers a wrong user name or password with a plain `AUTH_FAILED` (no reason, no keywords) as a control message after its key exchange message, over UDP and TCP; the client's key exchange has completed by then, so only the message ends the handshake. The `reason` is empty (`TestKeyExchangeWithRealServer`, step 2.3). The other forms (`SESSION:`, `TEMP[...]`, `HALT`, `RESTART`, `AUTH_PENDING`) are tested with the in-process peer only: the server sends them for a script, plugin or management decision that the test server does not make.

- **O20** A real server 2.7.9 with `--disable-dco` answers ICMP echo requests sent to its tunnel address with each of AES-256-GCM, AES-128-GCM, AES-192-GCM (when the client offers it, `DataCiphers`) and CHACHA20-POLY1305, over UDP and over TCP: 100 requests in a row for each of the eight, every reply back in a fraction of a second. So the format of §10 is exact: the keys of the TLS exporter with the directions as the draft names them, the nonce (packet id, then 8 bytes of the second key), the additional data (the header of `DATA_V2`), the tag before the ciphertext, ids from 1, and ids in order on TCP (a userspace server never skips one; a server with DCO does, O31). The server logs `Outgoing Data Channel: Cipher 'CHACHA20-POLY1305' initialized with 256 bit key` and the same for `Incoming` (`TestEchoWithRealServer`, step 2.5). The kernel data channel (DCO) was not tried: it cannot run in the test namespace (O17).

- **O21** With `IV_PROTO` bit 10 a real server 2.7.9 (`--disable-dco`) pushes `protocol-flags aead-epoch` (and `key-derivation tls-ekm`, as it has no `cc-exit` or `dyn-tls-crypt` flags to announce for this client) for each of the four data ciphers, over UDP and TCP, and the epoch format of §10 works with it at the first try: 100 echo requests in a row for each of the eight rows, and with the 32-bit format (bit 10 left out) for the other eight. With a client usage limit of 60 (a test knob) the client goes through 67 epochs in 600 requests: the server logs `Received data packet with new epoch N. Updating receive key` for each, moves its own packets to the epochs of the client, and the client opens them. The server derives its keys as it logs `Incoming Epoch Data key N: Cipher 'X' initialized` for the epochs 1 to 5 at once, which are its current and four future keys (`TestEchoWithRealServer`, `TestEpochsAdvanceWithRealServer`, step 2.6).

- **O22** When a real server (UDP) is killed, the next packet that the client sends makes the kernel report the ICMP port unreachable, and the next `Read` of the socket fails with `read udp ...: connection refused`: one second after the death with `--keepalive 1 3`. A client that ended the session there would not wait for the server to come back, and not use its `PingTimeout`; this one ignores the error (SPEC §11.1), pings on, and ends with `TagPingTimeout` exactly 3 seconds after. Over TCP the link ends (`EOF`) at once and the session ends with `TagLinkFailed`. An idle `Conn` of a `--keepalive 1 3` server is still usable after 10 seconds, over both links (`TestKeepaliveWithRealServer`, step 2.7).

- **O23** A real server 2.7.9 in server mode never sends `EXIT`: it is a message that clients send. When it stops it sends `RESTART` to its UDP clients if it has `--explicit-exit-notify` (and only then; the session then ends with `TagServerRestart`), and nothing to a TCP client, whose link just ends (`TagLinkFailed`, cause `io.EOF`); a client that hears nothing finds out by the keepalive. So the plan's "stopping the server gives `io.EOF`" cannot be shown against the real server; the `io.EOF` of §5.3 is tested with the in-process peer, which sends `EXIT` (`TestServerStopWithRealServer`, step 2.8).
- **O24** Both exit messages of the client are understood by a real server 2.7.9, over UDP and TCP (cc-exit) and over UDP (data channel): it logs `CC-EEN exit message received by peer` and `Delayed exit in 5 seconds`, or `OCC exit message received by peer` and `SIGUSR1[soft,remote-exit] received, client-instance restarting`, within a few hundred microseconds of `Close` on the loopback; `Close` itself takes about 0.1 to 0.4 ms, the time of the acknowledgement (`TestCloseWithRealServer`, step 2.8).
- **O25** A real server 2.7.9 renegotiates as §11.3 says, and no packet is lost: with `--reneg-sec 3` and a client that sends 10 ICMP echo requests a second, every request is answered across 13 renegotiations in 40 seconds (UDP with `tls-crypt`, and TCP with no protection), and across 2 or 3 in 9 seconds for UDP and TCP with each of no protection, `tls-auth` (SHA-1 and SHA-256), `tls-crypt` and `tls-crypt-v2`, for the epoch format and for the format with 32-bit packet ids. With the client's `RenegotiateAfter` of 3 seconds and the server's default, the client starts them, also with no loss. The server logs `TLS: soft reset sec=3/3 bytes=0/-1 pkts=0/0 aead_limit_send=0/60129542137 ...`, then `P_CONTROL_SOFT_RESET_V1 kid=1` written and read, then a new `Control Channel: TLSv1.3, cipher TLSv1.3 TLS_AES_256_GCM_SHA384` line for each new key (`TestRenegotiationWithRealServer`, `TestRenegotiationOfAMinuteWithRealServer`, `TestClientRenegotiationWithRealServer`, step 2.9).
- **O26** With `IV_PROTO` bit 9 the server pushes `protocol-flags cc-exit tls-ekm dyn-tls-crypt` and, once the push reply is sent, logs `Outgoing dynamic tls-crypt: Cipher 'AES-256-CTR' initialized with 256 bit key` and the same for `Incoming`, with no protection, `tls-auth`, `tls-crypt` and `tls-crypt-v2` alike: so even a server that protects nothing in the first session wraps its renegotiations. The key of §7.1 (exporter bytes XORed with the static key, `tls-crypt` form, client direction inverse) is the one it uses: every soft reset of the client and its TLS session are accepted, which they would not be with any other key.
- **O27** The real `openvpn` 2.7.9 client reads the same profile file that `ovpn.ParseFS` reads (inline CA, certificate, key and `tls-crypt`, `auth-user-pass creds.txt`, `remote ... udp`): run with `--cd <dir> --config client.ovpn --dev null --ifconfig-noexec --route-noexec` against the test server it logs `Initialization Sequence Completed` (step 3.3, `TestProfileOpenVPNClient`). `--cd` makes it find `creds.txt` as `ParseFS` does.
- **O28** Wine reaches the loopback of the namespace of `scripts/vpn-ns.sh` (it uses the network of the process), so a program built for Windows runs against the real server there: `ping.exe` over UDP and TCP and `http.exe` get their answers (step 4.1, `TestPingForWindowsUnderWine`, `TestHTTPForWindowsUnderWine`). The error of a refused connection is `WSAECONNREFUSED` on Windows, not `syscall.ECONNREFUSED`.
- **O29** gVisor's stack sends no ICMP error for a UDP datagram to a closed port, so a DNS server that is down is a timeout of the resolver and not a refusal (step 3.5, `TestDNSServerSelection`).
- **O30** Under heavy loss on a UDP tunnel a TCP connection of `vpnnet` with both directions saturated can stall for minutes against a Linux peer (§13, "Known limit"; step 4.2, the finding in `docs/IMPLEMENTED.md`).
- **O31** A real server 2.7.9 with the kernel data channel (DCO, Linux 7.3's `ovpn`, the default when the kernel has it) **drops data packets on a TCP link** when its socket is full, after their packet ids were used: a 1 MB download through `vpnnet` made the server's tun count 9 dropped packets, so the client saw ids with gaps (step 5.1). OpenVPN's own client takes them, because its replay window is `DEFAULT_SEQ_BACKTRACK` (64) on every protocol (`options.c`; `packet_id_test`'s branch "used with TCP" runs only with `--replay-window 0`). This library's client had strict order on a stream link, refused every packet after the first gap (`DataPacketReplayed`) and the download stalled; with the window it passes (20 MB over TCP and UDP, the SHA-256 of the server's file, with dozens of drops on the server). The userspace server (`--disable-dco`, what the tests in the namespace run, O17) never drops on TCP, which is why the steps before 5.1 did not see it.
- **O32** **The audit after 1.0** (2026-11-22, after O31 was found on the Mac): five reviews of the code against OpenVPN 2.7.9's source, each of one part, looking for what O31 was, an assumption that holds on the test setup and not against a real server or network. The wire formats, the replay windows, the AEAD and epoch formats, the control channel (its replay protection has the window on every link), the key ids and the key swap of a DCO server all match. What did not, and was fixed (each with a test that fails before the fix; `docs/IMPLEMENTED.md` has the list): the keepalive ping that stopped after one late wake of the loop (§11.1); `remote-cert-tls server` taking a certificate with no usage (§4.1); a stream link that takes no bytes stopping the loop, its timers and `Close` (§11.1); one failed write of a datagram link ending the session (§11.1); the retry of a failed renegotiation, which a real server cannot take (§20 V11); `connect-timeout` bounding the whole handshake (§12); a pushed option that cannot be read ending the handshake (§9); options of real profiles that made `ovpn.Parse` fail (§12); three faults of the DNS client of `vpnnet` (§13); `HandshakeContext` with a context that is done ending a session that is up; `DialContext` by name giving all the time to the first address (§13). None of it was run against a real server with the kernel data channel or over a real network: the tests are of the in-process peer and of the userspace server in the namespace. **Not settled then, and settled in O34:** with a DCO server nobody lowers the TCP MSS inside the tunnel (the userspace server does it for both directions, `mssfix`; `dco_linux.c dco_set_peer` does not pass it to the kernel), so over a real 1500-byte path the full segments of `vpnnet` would travel as IP fragments, which some networks drop.
- **O33** **The rest of the audit** (2026-11-22; the minor findings of O32, fixed at the owner's word). Shown by tests against the in-process peer, and against the real server 2.7.9 where it says so. (1) **A message of the control channel must be one TLS record.** `crypto/tls` cuts the first writes of a connection into records of about 1200 bytes (its dynamic record sizing), and OpenVPN reads one record at a time into its message buffer (`ssl.c key_state_read_plaintext`): of a key exchange message of 1400 bytes the real server read the first record, found a password that ended too early and answered `AUTH_FAILED,Username or password is too long. Maximum length is 128 bytes` (its log: `TLS Error: Username (201) or password (1101) too long`), though it takes 4095 bytes of each (built with PKCS#11). With the sizing off it logs in (`TestLongCredentialsWithRealServer`, UDP and TCP: a user name of 200 bytes, a password of 1100, the peer info after them read whole). Before, this was hidden by the client's own limit of 127 bytes, and showed only with a large `Config.PeerInfo`. The server's `--auth-user-pass-verify ... via-file` cannot write a password of more than 512 bytes (`could not write username/password to file`), and `--username-as-common-name` refuses a user name of more than 64: limits of those options, not of the protocol; the test uses `via-env`. (2) **Over UDP a real server at the third address of a name is reached** after a first address whose port is closed (an ICMP error ends the attempt at once) and a second that is silent (`ServerPollTimeout`, 2 s): `TestDialNextAddressWithRealServer`, 2.0 s. (3) **An interrupted program says goodbye:** the `ping` example, stopped by an interrupt signal in the middle of its pings, exits with status 130 within milliseconds and the server logs `CC-EEN exit message received by peer` (`TestPingInterruptedWithRealServer`). (4) Not run against a real server: `EXIT` in the middle of a renegotiation (the window is a fraction of a second once an hour; the in-process peer was made to read `EXIT` on its newest key only, as `ssl.c` does), the pushed `ping-exit`, and the race of a stray soft reset with the making of the dynamic tls-crypt key (the race detector shows it on the old code).
- **O34** **The MSS with a DCO server over a real network** (2026-11-22; the Mac and the Fedora VM on UTM's network, 1500-byte path, OpenVPN 2.7.9 with the kernel data channel of Linux 7.3, `tls-crypt`, AES-256-GCM, 20 MB each way through `vpnnet` to a sink and a source in the VM, captured on the VM's interface and its tunnel device). **Before the fix (v1.0.1):** the SYNs crossed the tunnel with MSS 1460 both ways, and the full segments, in their OpenVPN packets of up to 1524 bytes, left as two IP fragments each: 14,556 datagrams of the Mac and 13,812 of the VM. With every IP fragment dropped on the VM's interface (an `nft` rule of the netdev family) both transfers stalled at 0 bytes while the session stayed up. The same server with `--disable-dco` sent no fragment: its userspace data channel lowered the MSS to 1396 (epoch format: 1492 - 28 - 28 - 40). **After the fix (§10, the clamp in the `Conn`):** `ConnectionState.MSS` 1400 on UDP and 1386 on TCP, the SYNs on the server's tunnel device with those values, no fragment either way (the largest IP packet 1492 bytes), and with fragments dropped both transfers of 20 MB completed with the right SHA-256 (the drop rule counted 0 packets). The server's SYN-ACK still announces 1460 inside the tunnel: the client lowers it when it reads it. `TestRealServerMSS` (vpnnet, the userspace server in the namespace, UDP and TCP, `--mssfix 0` so that only the client clamps; it negotiates the epoch format, so the MSS is 1396 on UDP and 1382 on TCP) reads the MSS that the server's TCP stack took: `TCP_MAXSEG` 1384 and 1370 over IPv4 (the MSS less the 12 bytes of the timestamps option), 20 less over IPv6.
